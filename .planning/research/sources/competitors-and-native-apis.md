## 0. TL;DR

- **The incumbent is still winning on distribution, not on code.** `video_compress` does **167,492 downloads/30 d, 747 likes** vs the best challengers at 15,110 (`light_compressor_v2`), 11,787 (`v_video_compressor`) and 41,514 (`ffmpeg_kit_flutter_new`) — pub.dev `/score` endpoints. Its repo has **208 open issues / 344 forks / 262 stars** and no commit since 2025-02-13 (`gh api repos/jonataslaw/VideoCompress`). Its Android side is 384 lines of Kotlin wrapping **otaliastudios `transcoder:0.10.5`** (`VideoCompress/android/build.gradle:59`), a library that itself has had **no release since v0.11.2 on 2024-11-05** and only emits H.264 (`Transcoder/lib/src/main/java/com/otaliastudios/transcoder/strategy/DefaultVideoStrategy.java:124`).
- **Two native-only challengers exist and both are one-person projects.** `light_compressor_v2` (raw MediaCodec + OpenGL on Android, AVAssetReader/Writer on iOS, 4,089 kt + 3,464 swift, 4 stars, one maintainer) and `v_video_compressor` (Media3 Transformer 1.8.0 on Android, AVAssetExportSession on iOS, 3,683 kt + 2,784 swift, 14 stars, effectively one maintainer under an org name). A third, `flutter_compress` (2.0.0, 2026-08-30), is the only one with a **web** target (WebCodecs + mp4box/mp4-muxer) and the only one that sets an explicit Media3 `VideoEncoderSettings` bitrate.
- **The right modern stack is clear:** Android → **Media3 Transformer** (stable 1.11.0, 2026-08-05; pure Kotlin/Java, ~4 MB of AARs before shrinking, no `.so` so no 16 KB page-size exposure, built-in HDR tone-mapping, transmuxing, trim, `Presentation` resize, progress + cancel; minSdk 23 since 1.9.0). iOS/macOS → **AVAssetReader + AVAssetWriter** (real bitrate control via `AVVideoAverageBitRateKey`, HEVC via `AVVideoCodecType.hevc`, HDR via `AVVideoColorPropertiesKey`), with **AVAssetExportSession** as a fallback for presets/passthrough — noting its `progress` property is **deprecated in iOS 27** in favour of `states(updateInterval:)` (iOS 18+).
- **The hard parts that sink every package in this space** are HDR (iPhone shoots Dolby Vision/HLG by default; an SDR pipeline yields washed-out output), rotation metadata, audio passthrough vs re-encode, iOS background suspension (`-11847 Operation Interrupted` is *expected behaviour* per an Apple engineer), and Android foreground-service rules. Sections 3–5.

### 1.2 light_compressor_v2 — "raw MediaCodec, no deps, one maintainer"

- **Lineage:** a fork of the archived `light_compressor` that vendors AbedElazizShe's Android `LightCompressor` library in-tree (`android/src/main/kotlin/com/gurfdev/light_compressor_v2/lightcompressorlibrary/…`: `Compressor.kt`, `InputSurface.kt`, `OutputSurface.kt`, `TextureRenderer.kt`, `VideoResizer.kt`). The original depended on the same code as a JitPack AAR (`light_compressor/android/build.gradle:45`).
- **Dart surface** (`lib/src/light_compressor.dart:163-330`): `compressVideo({path, videoQuality, android: AndroidConfig(isSharedStorage, saveAt), ios: IOSConfig(saveInGallery), video: Video(videoName, keepOriginalResolution, videoBitrateInMbps, videoHeight, videoWidth, targetSizeMb, videoFps, twoPass), disableAudio, isMinBitrateCheckEnabled, videoFormat: h264|h265, background: BackgroundConfig, audio: AudioConfig(bitrate, sampleRate), edit: VideoEdit(trimStartMs, trimEndMs, rotationDegrees, brightness, contrast, saturation), debugLogging})` → sealed `Result` (`OnSuccess{destinationPath, originalSize, compressedSize, duration, ratio, usedFormat, targetSizeMet, passesUsed}` / `OnFailure{failureType}` / `OnCancelled`) plus typed exceptions (`PermissionDenied`, `UnsupportedVideo`, `VideoNotFound`, `MediaInfo`, `Thumbnail`, `Estimate`). Batch `compressVideos(... maxConcurrent)`, `getMediaInfo`, `getVideoThumbnail(s)`, `getCompressionEstimate` (no transcode), `clearCache`, `cancelCompression`, `isCompressing`; streams `onProgressUpdated`, `onProgressDetail` (percent, `etaMs`, `elapsedMs`, `bytesProcessed`), `onBatchUpdate`.
- **Android internals:** `MediaExtractor` → `MediaCodec` decoder → GL `OutputSurface`/`InputSurface` → `MediaCodec` encoder → `MediaMuxer`. HEVC only when a *hardware* encoder exists (software `c2.android.*`/`OMX.google.*` excluded, `CompressorUtils.kt:213-225`); falls back to H.264 and reports `usedFormat`. CBR requested (`CompressorUtils.kt:89-90`), two-pass corrective re-encode when `targetSizeMb` is missed (`Compressor.kt:343-402`). Rotation is **metadata-only** — `MediaMuxer.setOrientationHint(rotation)` (`Compressor.kt:317-319, 519`). Colour: copies `KEY_COLOR_STANDARD/TRANSFER/RANGE` from the input format onto the encoder format (`CompressorUtils.kt:92-104`) — i.e. an HDR source's transfer characteristic is stamped onto an 8-bit GL-rendered output; there is no tone-mapping step (no `hdr|HLG|tone` hits in `android/src`).
- **Background:** Android foreground service typed `dataSync` with `FOREGROUND_SERVICE_DATA_SYNC` and `POST_NOTIFICATIONS` permissions (`AndroidManifest.xml:7-15`, `CompressionForegroundService.kt:48-51`). iOS: "**not supported.** iOS suspends backgrounded apps within seconds … there is no sanctioned way to keep video transcoding running in the background" (`lib/src/background_config.dart:29-35`). macOS suppresses App Nap.
- **iOS/macOS internals:** `AVAssetReader` + `AVAssetWriter(outputURL:fileType: .mp4)`, `AVVideoAverageBitRateKey`, `.hevc`/`.h264` (`LightCompressor.swift:770-900, 1152-1154`); HEVC capability probed via `AVAssetExportSession.allExportPresets().contains(AVAssetExportPresetHEVCHighestQuality)` (line 1142); audio passthrough via `AVAssetWriterInput(... sourceFormatHint:)` or AAC re-encode.
- **Signals of thin real-device testing:** 1.9.0 fixed a crash that "reproduc[ed] 100% on a physical iOS device" for any `.mov` with audio because the passthrough input lacked a format hint, and 1.9.1 fixed "a compression could end with no result at all" (`CHANGELOG.md` 1.9.0/1.9.1). README warns "an output approaching 4 GB may fail or truncate" (`README.md:433`). Windows/Linux "not planned"; web not offered (`README.md:45-52`).
- **Clever:** `getCompressionEstimate` pre-flight, `usedFormat`/`passesUsed`/`targetSizeMet` in the result, typed exceptions, batch concurrency cap. **Missing:** HDR tone-mapping, any iOS background story, crop, frame-accurate trim via edit lists.

### 1.3 v_video_compressor — "Media3 Transformer + AVAssetExportSession, ffmpeg-shaped options"

- **Dart surface** (`lib/v_video_compressor.dart:157-412`, `lib/src/v_video_models.dart`): `compressVideo(path, VVideoCompressionConfig(quality: high|medium|low|veryLow|ultraLow, outputPath, deleteOriginal, fallbackToOriginalIfNotSmaller, saveToGallery, includeAudio, includeMetadata, optimizeForStreaming, copyMetadata, useHardwareAcceleration, useFastStart, useTwoPassEncoding, useVariableBitrate, advanced: VVideoAdvancedConfig(videoBitrate, audioBitrate, customWidth/Height, frameRate, videoCodec h264|h265, audioCodec aac|mp3, encodingSpeed ultrafast…veryslow, crf, twoPassEncoding, trimStartMs/EndMs, rotation, cropRect, audioSampleRate, audioChannels, removeAudio, autoCorrectOrientation, brightness/contrast/saturation, variableBitrate, keyframeInterval, bFrames, reducedFrameRate, aggressiveCompression, noiseReduction, monoAudio, dimensionHandling autoAlign|letterbox|exact)), onProgress)`, `compressVideos`, `getVideoInfo`, `getCompressionEstimate`, `getVideoThumbnail(s)`, `cancelCompression`, static `listen*` streams, `configureLogging`.
- **Observation:** `crf`, `encodingSpeed` (x264 preset names), `bFrames`, `noiseReduction`, `audioCodec.mp3` are **ffmpeg vocabulary** that neither Media3 Transformer nor AVAssetExportSession can honour; the README itself admits "On iOS, `videoBitrate` is approximated through AVFoundation's total output-size limit … `audioBitrate` is not an [option]" (`README.md:645-646`). The option surface overstates what the engines do.
- **Android internals:** `Transformer.Builder(context).setMuxerFactory(InAppMp4Muxer.Factory()).setVideoMimeType(...)`, `ScaleAndRotateTransformation`, `Presentation.createForWidthAndHeight(... LAYOUT_SCALE_TO_FIT)`, `Crop`, `MediaItem.ClippingConfiguration`, `setRemoveAudio`, `transformer.cancel()`, progress polling (`VVideoCompressionEngine.kt:971-990, 1454-1466, 1696-1752`). Per-quality bitrate constants (8 Mbps 4K … 200 kbps 240p, lines 108-114) are chosen at lines 491-530, but **no `VideoEncoderSettings`, `DefaultEncoderFactory` or `KEY_BIT_RATE` appears anywhere in `android/src`** — so on Android the requested bitrate seemingly never reaches the encoder; size is governed by resolution and Media3's default bitrate heuristics. Worth verifying before trusting `videoBitrate` on Android. No HDR handling found (no `hdr|COLOR_TRANSFER|tone` hits).
- **iOS internals:** `AVAssetExportSession(asset:presetName:)` with `shouldOptimizeForNetworkUse = true`; when HEVC is available *all* qualities map to `AVAssetExportPresetHEVC1920x1080` or `HEVCHighestQuality` (`VVideoCompressionEngine.swift:732-736`) — i.e. "veryLow/ultraLow" is still a 1080p HEVC preset and size is throttled only by `fileLengthLimit` (`VVideoFileLengthBudget.swift`, engine line 308-316). Crop/rotate/resize via `AVMutableVideoComposition` (lines 396-456). Progress by `Timer` polling `exportSession.progress` (line 751) — that property is deprecated as of iOS 27 (see §2.2).
- **Provenance:** merge commits come from `codex/release-*` branches (`git log`), i.e. AI-assisted releases; 2.2.0 added a "simulator audit with native track and decoded-pixel inspection" (`CHANGELOG.md`). No background support.

### 1.4 ffmpeg_kit_flutter_new — "the toolkit, not a compressor"

- Maintained fork of Arthenica's abandoned FFmpegKit Flutter binding; **FFmpeg 8.1.2** with VideoToolbox on Apple platforms; eight variants (`min` … `full-gpl`) (`README.md:1-60`). Dart API is `FFmpegKit.execute('-i in.mp4 -c:v … out.mp4')` + `FFprobeKit`, sessions, log/statistics callbacks, cancel — `lib/ffmpeg_kit.dart`, `lib/ffprobe_kit.dart`, `lib/statistics_callback.dart`.
- **Cost:** Android `ffmpeg-kit-full-gpl:2.2.1` AAR is **108.9 MB** on Maven Central (all ABIs; the per-ABI install is smaller but still tens of MB); iOS downloads 8 xcframeworks at `pod install` from a GitHub release (`scripts/setup_ios.sh:22-24`) — release zips: `video` 29 MB, `min-gpl` 25 MB, `min` 22 MB (`gh api …/releases`). The full-gpl variant is **GPL v3** in effect (`README.md:276`), which is a hard blocker for many app publishers. 16 KB compliance required a re-uploaded AAR (`CHANGELOG.md:126`).
- Everything is *possible* (HDR tone-map with `zscale`/`tonemap`, precise CRF, HEVC via x265) but software x264/x265 on a phone CPU is slow and hot; hardware paths (`h264_mediacodec`, `hevc_videotoolbox`) exist but need per-platform command strings. Not a drop-in `compressVideo()`.

## 2. Modern native APIs

### 2.1 Android — Media3 Transformer vs Transcoder vs raw MediaCodec

**Media3 Transformer** (`androidx.media3.transformer`), stable **1.11.0 released 2026-08-05**; prior 1.10.0 (2026-03-26), 1.9.0 (2025-12-17) — https://developer.android.com/jetpack/androidx/releases/media3. `minSdk` was raised to **21 in 1.5.0 (2024-11-27)** and to **23 in 1.9.0** ("Update `minSdk` to `23` in line with other AndroidX libraries") — `media3src/RELEASENOTES.md:899-902, 2260-2274` (mirror of https://github.com/androidx/media/blob/release/RELEASENOTES.md). 1.9.0 also made `InAppMp4Muxer` the default muxer.

- **What it does** (https://developer.android.com/media/media3/transformer/getting-started and `/transformations`): `Transformer.Builder(context).setVideoMimeType(MimeTypes.VIDEO_H264 | VIDEO_H265).setAudioMimeType(MimeTypes.AUDIO_AAC).addListener(...).build()` then `transformer.start(editedMediaItem, outputPath)`. "If input media format already matches the configured audio/video formats, Transformer automatically switches to **transmuxing**" (no re-encode). Output "is always an MP4 file" and "always a progressive stream". Trim via `MediaItem.ClippingConfiguration.Builder().setStartPositionMs().setEndPositionMs()`; faster trims via `experimentalSetTrimOptimizationEnabled(true)` and `experimentalSetMp4EditListTrimEnabled(true)` (caveat: "deleted sections remain in the file but hidden"). Resize via `Presentation.createForHeight(480)` / `createForWidthAndHeight(w, h, LAYOUT_SCALE_TO_FIT)`, or `ScaleAndRotateTransformation.Builder().setScale(.5f,.5f)` / `.setRotationDegrees(90f)`. Audio strip via `EditedMediaItem.Builder.setRemoveAudio(true)`. Progress: poll `transformer.getProgress(ProgressHolder)`; state `PROGRESS_STATE_AVAILABLE` fills the percentage. Cancel: `Transformer.cancel()`. Listener `onCompleted(composition, ExportResult)` / `onError(..., ExportException)`. Constraints: "Transformer instances must be accessed from a single application thread" and "concurrent exports with the same instance are not supported".
- **Bitrate / codec:** `Transformer.Builder.setEncoderFactory(DefaultEncoderFactory.Builder(ctx).setRequestedVideoEncoderSettings(VideoEncoderSettings.Builder().setBitrate(int).setBitrateMode(int).setEncodingProfileLevel(profile, level).setiFrameIntervalSeconds(float).setEncoderPerformanceParameters(operatingRate, priority).setMaxBFrames(int).setTemporalLayers(...).build()).setEnableFallback(bool).build())` — `media3src/VideoEncoderSettings.java:125-244`, `media3src/DefaultEncoderFactory.java:119-211` (mirrors of https://github.com/androidx/media/tree/release/libraries/transformer/src/main/java/androidx/media3/transformer). "Bitrate settings in `Format` are ignored when `VideoEncoderSettings#bitrate` is set" (`DefaultEncoderFactory.java:322-323`). Default audio bitrate 128 kbit/s (line 58). `setEnableCodecDbLiteBitrate` lets Google's CodecDB recommend a bitrate (line 173).
- **Rotation:** `setPortraitEncodingEnabled(false)` is the default: "portrait videos will be rotated by 90 degrees before being encoded, and metadata will be added to the output file to indicate that the video should be rotated back when played. This is done because encoding landscape videos is more largely supported" (`media3src/Transformer.java:329-341`). So Transformer handles the classic sideways-video bug for you.
- **HDR / tone-mapping** (`media3src/Composition.java:315-368`; https://developer.android.com/media/media3/transformer/supported-formats): `Composition.Builder.setHdrMode(...)` with `HDR_MODE_KEEP_HDR` (default; "Supported on API 31+, by some device and HDR format combinations. If not supported, Transformer will attempt to use HDR_MODE_TONE_MAP_HDR_TO_SDR_USING_OPEN_GL"), `HDR_MODE_TONE_MAP_HDR_TO_SDR_USING_MEDIACODEC` ("API 31+ … only guaranteed on API 33+ on devices with HDR capture support"), `HDR_MODE_TONE_MAP_HDR_TO_SDR_USING_OPEN_GL` ("Supported on API 29+ … much wider support and more consistent results"), and experimental `FORCE_INTERPRET_HDR_AS_SDR` ("contents will be displayed incorrectly, likely with a washed out look"). Docs add: HDR editing API 33+, "Dolby Vision (profile 8) transmuxing and transcoding with tone-mapping", Ultra HDR→HDR.
- **Encoding limits:** "Transformer also relies on `MediaCodec` for encoding, which limits the output formats supported" (supported-formats page). Per https://developer.android.com/media/platform/supported-formats: HEVC encoder Android 5.0+ (Main Profile Level 3 mobile), H.264 Main encoder 6.0+, AV1 encoder 14+ / decoder 10+.
- **Size / 16 KB:** the 1.11.0 AARs are `media3-transformer` 0.5 MB, `-effect` 0.4, `-common` 0.6, `-muxer` 0.1, `-exoplayer` 1.6, `-extractor` 0.8, `-datasource` 0.2, `-container` 0.1 (`curl -sI https://dl.google.com/dl/android/maven2/androidx/media3/<artifact>/1.11.0/…aar`) — pure JVM bytecode, R8-shrinkable, and no `.so`, so "If your app only uses code written in the Java programming language or in Kotlin … your app already supports 16 KB devices" (https://developer.android.com/guide/practices/page-sizes).

**otaliastudios / deepmedia Transcoder** — https://github.com/deepmedia/Transcoder: 864 stars, 181 forks, 32 open issues, Apache-2.0; last release **v0.11.2 on 2024-11-05**, last commit the same day (`gh api repos/deepmedia/Transcoder`, `/releases`, `/commits`). Artifact `io.deepmedia.community:transcoder-android:0.11.2` (`Transcoder/README.md`). "Fast transcoding to AAC/AVC", API 21+, trim/clip, concatenate, size/rotation/speed/frame-rate strategies. Only `MIMETYPE_VIDEO_AVC` is defined and it is the default target (`DefaultVideoStrategy.java:124`; `MediaFormatConstants.java:48`). Open issues include **#191 "HDR Tone Mapping"** (2025-07-28), #218 "App Killed During Parallel Video Compression", #214 "Timestamps must be monotonically increasing" (`gh api …/issues?state=open`). `video_compress` pins the older `com.otaliastudios:transcoder:0.10.5`. Verdict: not archived, but 22 months without a commit, H.264-only, no HDR — a dependency to migrate off, not onto.

**Raw MediaCodec/MediaExtractor/MediaMuxer** (what `light_compressor_v2` does): full control and no dependency, but you own the GL surface plumbing, codec quirks, colour-format negotiation, HDR (10-bit surfaces + tone-mapping shaders), muxer timestamp rules, and the fallback matrix across OEM encoders — roughly 4,000 lines of Kotlin in `light_compressor_v2` for a feature set Transformer provides.

### 2.2 iOS / macOS — AVAssetExportSession vs AVAssetReader/AVAssetWriter

All Apple facts below were read from the JSON that backs each documentation page (`https://developer.apple.com/tutorials/data/documentation/<path>.json`, saved under `appledocs/`); the human URL is `https://developer.apple.com/documentation/<path>`.

**AVAssetExportSession** (iOS 4+) — `avfoundation/avassetexportsession`: "exports assets in a format that you specify using an export preset". Presets (`avfoundation/export-presets`):
- Quality: `AVAssetExportPresetLowQuality`, `MediumQuality`, `HighestQuality` — each "compresses video in H.264 format and audio in AAC format"; no documented target resolution or bitrate.
- Size: `640x480`, `960x540`, `1280x720`, `1920x1080`, `3840x2160` — "A preset to export a 1280 by 720 movie that contains H.264 video and AAC audio. The system doesn't scale movies up from a smaller size."
- HEVC (iOS 11+): `HEVC1920x1080`, `HEVC3840x2160`, `HEVCHighestQuality` ("highest available video quality and HEVC video compression"), plus `…WithAlpha`, `HEVC4320x2160`, `HEVC7680x4320`, MV-HEVC, ProRes, M4V, `AppleM4A`.
- `AVAssetExportPresetPassthrough`: "export the asset in its current format … doesn't show up in `allExportPresets()`".
- **Bitrate cannot be set.** The "Configuring output" topic lists only `supportedFileTypes`, `allowsParallelizedExport` (macOS 14 only), `shouldOptimizeForNetworkUse`, `canPerformMultiplePassesOverSourceMediaData` (iOS 8, default `false`, "may also require the export session to write temporary data to disk"), `timeRange`, `fileLengthLimit` ("The file length that the output of the session must not exceed"), `directoryForTemporaryFiles`. `fileLengthLimit` is the only size lever — which is why `v_video_compressor` builds a "file length budget" around it.
- `videoComposition`/`customVideoCompositor`, `audioMix`, `metadata`, `estimateOutputFileLength(completionHandler:)` (iOS 13) / `estimatedOutputFileLengthInBytes` async.
- **Progress & cancel:** `progress` ("ranges from 0.0 to 1.0") is **deprecated in iOS 27.0 / macOS 27.0**; the replacement is `states(updateInterval:)` → `AsyncSequence<AVAssetExportSession.State>` (iOS 18+), and `export(to:as:isolation:) async throws` (iOS 13+, back-deployed) where "you can cancel an in-progress export by calling `cancel()` on the Task". `cancelExport()` remains for the old path.
- **HDR behaviour** (WWDC20 session 10010, https://developer.apple.com/videos/play/wwdc2020/10010/): "We have upgraded the existing HEVC presets to preserve the source's HDR format. For example, HDR10 source assets will export as HDR10, HLG exports to HLG … In order to convert from HDR to SDR, we recommend that you use the H.264 presets which will also maximize backwards compatibility." HEVC hardware encode "on devices with Apple A10 Fusion chips or newer … iPhone 7".

**AVAssetReader + AVAssetWriter** (iOS 4.1+) — `avfoundation/avassetwriter`, `avfoundation/avassetreader`, `avfoundation/avassetwriterinput`:
- `AVAssetWriter` "can reencode media samples it writes to the output file" and is "a single-use object that writes one output file". `AVAssetWriterInput(mediaType:outputSettings:sourceFormatHint:)`; `outputSettings == nil` means "the input passes the samples through to the output without reencoding them" (`avassetwriterinput/outputsettings`) — the audio-passthrough path (and the one `light_compressor_v2` got wrong until 1.9.0 by omitting `sourceFormatHint`).
- Bitrate: `AVVideoAverageBitRateKey` — "the average bit rate—as bits per second—used in compressing video" (iOS 4). Codec: `AVVideoCodecType.hevc` (iOS 11). Profile: `AVVideoProfileLevelKey`. Frame-rate hint: `AVVideoExpectedSourceFrameRateKey` — "The encoder might have to drop frames to satisfy bit stream requirements if this key is not specified" for >30 fps sources. HDR: `AVVideoColorPropertiesKey` (iOS 10) "must contain the keys AVVideoColorPrimariesKey, AVVideoTransferFunctionKey, and AVVideoYCbCrMatrixKey"; WWDC20: HDR export needs HEVC/ProRes + HLG or PQ transfer + `HEVC_Main10_AutoLevel`.
- Rotation: `AVAssetWriterInput.transform` — "By default, the input uses the CGAffineTransformIdentity transform. You can't set this value after writing starts." Source orientation comes from `AVAssetTrack.preferredTransform` ("typically, but not always, CGAffineTransformIdentity"), whose synchronous getter is **deprecated since iOS 16** in favour of async `load(.preferredTransform)`.
- Progress: none built in — compute from the PTS of the last appended sample over the asset duration (this is what `light_compressor_v2` does; `LightCompressor.swift`). Multi-pass: `AVAssetWriterInput.canPerformMultiplePasses` / `performsMultiPassEncodingIfSupported` topic.
- **Background:** see §3.6.

### 2.3 Web

- **WebCodecs** (https://developer.mozilla.org/en-US/docs/Web/API/WebCodecs_API): `VideoEncoder`/`VideoDecoder`/`AudioEncoder`/`AudioDecoder`, hardware-accelerated; "only deals with encoding and decoding … does not provide a built-in way to read `EncodedVideoChunk` objects from a video file, or write them to a playable video file" — you need a demuxer/muxer (MDN names Mediabunny; `mediabunny` 1.56.2, MPL-2.0, published 2026-09-12 per npm registry). Browser support (caniuse `webcodecs.json`, https://github.com/Fyrd/caniuse/blob/main/features-json/webcodecs.json): full support Chrome/Edge 94, Firefox 130, **Safari/iOS Safari only from 26.0**; Safari 16.4–18 are flagged "a #1 — Video-only support" (no `AudioEncoder`). `flutter_compress` uses exactly this stack (WebCodecs + mp4box.js + mp4-muxer) and claims Safari 16.4+, presumably because it only needs the video half.
- **ffmpeg.wasm** (https://github.com/ffmpegwasm/ffmpeg.wasm, https://ffmpegwasm.netlify.app/docs/faq): `@ffmpeg/ffmpeg` 0.12.15 (MIT) and `@ffmpeg/core` 0.12.10 (npm licence field `GPL-2.0-or-later`), both last published 2025-01-07 (npm registry). `ffmpeg-core.wasm` is **30.7 MB** single-thread / **31.2 MB** multi-thread (`curl -sL -w %{size_download} https://cdn.jsdelivr.net/npm/@ffmpeg/core@0.12.10/dist/umd/ffmpeg-core.wasm`). Multithread needs `SharedArrayBuffer` → COOP/COEP cross-origin isolation headers (usage page → MDN "Security requirements"). FAQ: "WebAssembly is still a lot slower than native", mt "around 2x speed comparing to single thread", memory "2 GB, which is a hard limit in WebAssembly". Software-only encode.
- **MediaRecorder re-encode** (`<video>` → `canvas.captureStream()` → `MediaRecorder`, https://developer.mozilla.org/en-US/docs/Web/API/MediaRecorder): records a *live* stream, so it runs at 1× playback time, gives no precise bitrate/size control, container/codec choice is browser-dependent (WebM in Chrome/Firefox), and audio must be routed through the same stream. Fine for a demo, not for a "compress to ≤ 10 MB" API.
- Realistic position: a web target is feasible only on the WebCodecs path, at ~0.2 MB of JS, with Safari < 26 limited to video-only and Firefox < 130 excluded.

## 3. The hard parts

### 3.1 H.264 vs HEVC
- Android: HEVC *decoding* is required on Android 5.0+ (Main Profile Level 3 for mobile) and an HEVC *encoder* "Android 5.0+" but as a recommendation — many low-end devices expose only the AOSP software `c2.android.hevc.encoder`, which is why `light_compressor_v2` refuses software HEVC (`CompressorUtils.kt:213-225`) — https://developer.android.com/media/platform/supported-formats.
- Apple: HEVC hardware encode needs A10+ (iPhone 7, 2016) — WWDC20 10010. HEVC in `.mp4` plays on any iOS 11+ device.
- Recipients: caniuse `hevc.json` shows Chrome/Edge/Android Chrome "a" (partial: "for devices with hardware support"), Firefox "a" (Windows hardware only), Safari "y". Windows needs the HEVC extension. So **default to H.264 and offer HEVC as opt-in** with automatic fallback and a `usedFormat`-style report, as both `light_compressor_v2` and `flutter_compress` do.

### 3.2 HDR (Dolby Vision / HLG / HDR10)
- iPhones record HDR (Dolby Vision profile 8.4 = HLG-based) by default; Android requires "HLG10 … for user-generated content capture and playback" (supported-formats page). So a compressor *will* receive HDR input routinely.
- What goes wrong: feeding HDR frames through an 8-bit SDR pipeline yields the "washed out look" Media3 warns about for `FORCE_INTERPRET_HDR_AS_SDR` (`Composition.java:356-359`). `light_compressor_v2` copies the source `KEY_COLOR_TRANSFER` onto its 8-bit output (`CompressorUtils.kt:92-104`), which mislabels SDR-rendered pixels as HDR; `v_video_compressor` has no HDR code at all; Transcoder has an open "HDR Tone Mapping" issue (#191).
- Fixes available: Media3 `HDR_MODE_TONE_MAP_HDR_TO_SDR_USING_OPEN_GL` (API 29+) or keep-HDR (API 31+/33+); AVFoundation H.264 presets tone-map to SDR automatically, HEVC presets preserve HDR; with `AVAssetWriter`, choose either SDR output (8-bit reader output, encoder defaults) or explicit HDR output via `AVVideoColorPropertiesKey` + `HEVC_Main10_AutoLevel` (WWDC20 10010; Apple's Dolby Vision guide https://developer.apple.com/av-foundation/Incorporating-HDR-video-with-Dolby-Vision-into-your-apps.pdf). Policy decision for a rebuild: default to tone-mapped SDR H.264 for compatibility, opt-in HDR-preserving HEVC.

### 3.3 Rotation metadata
- Phones store portrait video as landscape frames plus a rotation flag (`METADATA_KEY_VIDEO_ROTATION` on Android, `preferredTransform` on Apple). If the pipeline decodes without applying it, encodes, and drops the flag, the result is sideways; if it applies it but also keeps the flag, it is doubly rotated; if it swaps width/height without rotating frames, you get letterboxed black bars. Media3 handles this by rotating to landscape and writing metadata (`Transformer.java:329-341`); raw MediaMuxer needs `setOrientationHint` (`Compressor.kt:519`); AVAssetWriter needs `input.transform = track.preferredTransform` set *before* writing starts (`avassetwriterinput/transform`). `v_video_compressor` adds `VDimensionHandling.letterbox` and 16-pixel alignment because encoder dimension constraints otherwise cause artefacts (`v_video_models.dart:5-13`). 7 of 233 `video_compress` issues are rotation reports.

### 3.4 Audio: passthrough vs re-encode
- Passthrough is free and lossless: Media3 transmuxes automatically when `setAudioMimeType` matches the source; AVAssetWriterInput with `outputSettings: nil` passes samples through, but needs `sourceFormatHint` or it throws on device (`light_compressor_v2/CHANGELOG.md` 1.9.0). Re-encode is needed for non-MP4-friendly sources (e.g. PCM/Opus into MP4), for bitrate reduction, and for mono downmix. `video_compress` exposes only `includeAudio`; 45 of its 233 issues mention audio.

### 3.5 Progress and cancel semantics
- Android Transformer: polled `getProgress(ProgressHolder)` with `PROGRESS_STATE_NOT_STARTED/WAITING/AVAILABLE/UNAVAILABLE`; progress is unavailable during transmux-only phases. `cancel()` is synchronous and the listener does not fire `onCompleted`.
- AVAssetExportSession: `progress` polling is deprecated (iOS 27); the modern contract is `states(updateInterval:)` + Task cancellation — a rebuild targeting iOS 13+ should use `export(to:as:)` and, on iOS 18+, `states`.
- AVAssetReader/Writer: no progress API; derive from sample PTS. Cancel = `reader.cancelReading()` + `writer.cancelWriting()` and delete the partial file.
- Cross-platform contract worth designing in: a cancelled job must resolve with a distinct `Cancelled` result (as `light_compressor_v2`'s `OnCancelled`), never a generic error.

### 3.6 Background execution
- **iOS:** `applicationDidEnterBackground` "has five seconds"; `beginBackgroundTask(withName:expirationHandler:)` grants "a finite amount of time … If you don't call `endBackgroundTask(_:)` for each task before time expires, the system kills the app" (`uikit/extending-your-app-s-background-execution-time`, `uikit/uiapplication/beginbackgroundtask(withname:expirationhandler:)`). An Apple media engineer on https://developer.apple.com/forums/thread/672056: "**This is expected behavior. The asset writer must give up encoding resources when your app goes into the background, and there is no way to reliably pick up where you left off**" — error `AVFoundationErrorDomain -11847 Operation Interrupted`. A rebuild must document this and surface a resumable/retry story (e.g. auto-restart on foreground), as `light_compressor_v2` does by declaring iOS unsupported.
- **Android:** a foreground service is required to keep transcoding when backgrounded. The dedicated type is `mediaProcessing` (`FOREGROUND_SERVICE_TYPE_MEDIA_PROCESSING`, permission `FOREGROUND_SERVICE_MEDIA_PROCESSING`, "Service for performing time-consuming operations on media assets, like converting media to different formats"), limited to "6 hours out of every 24" shared across the app's media-processing services, with `Service.onTimeout()` and an ANR if you don't `stopSelf()` — https://developer.android.com/develop/background-work/services/fgs/service-types. `light_compressor_v2` uses the `dataSync` type instead (`AndroidManifest.xml:15`), which the same page restricts further on Android 15.

### 3.7 Very large files (4K60, multi-GB)
- MediaCodec capability limits (HEVC Main L3 is the *minimum* mobile requirement — a 4K60 encode needs a Level 5.1+ encoder, which `MediaCodecInfo.VideoCapabilities` must be queried for; `v_video_compressor` does this in `VVideoCompressionEngine.kt:451-467`). Transformer exposes `experimentalSetMaxFramesInEncoder` to bound in-flight frames (`Transformer.java:425`).
- Apple: set `AVVideoExpectedSourceFrameRateKey` for >30 fps sources or "the encoder might have to drop frames"; multi-pass (`canPerformMultiplePassesOverSourceMediaData`) writes temp data to disk.
- File-size ceilings: `light_compressor_v2` warns "an output approaching 4 GB may fail or truncate" (`README.md:433`); ffmpeg.wasm is capped at 2 GB of memory. Time: hardware paths run at several × realtime; anything software (x264/x265, wasm) is slower than realtime on phones.

### 3.8 16 KB page size (Google Play)
- "Starting November 1st, 2025, all new apps and updates to existing apps submitted to Google Play and targeting Android 15+ devices must support 16 KB page sizes" — https://android-developers.googleblog.com/2025/05/prepare-play-apps-for-devices-with-16kb-page-size.html. The developer guide currently reads "Starting February 1, 2027, if your app updates don't support 16 KB memory page sizes, you won't be able to release these updates" for "all apps targeting Android 15 (API level 35) and higher" — https://developer.android.com/guide/practices/page-sizes (Play Console extension threads exist — e.g. https://support.google.com/googleplay/android-developer/thread/368982598 — but their bodies were not fetchable here, so treat exact extension dates as unverified).
- Only native `.so` code is affected: "If your app only uses code written in the Java programming language or in Kotlin … your app already supports 16 KB devices." NDK r28+ aligns by default; AGP 8.5.1+ needed for uncompressed-library zip alignment; check with `zipalign -c -P 16 -v 4 app.apk` or `check_elf_alignment.sh` (same page).
- Consequence: a Media3/MediaCodec-based plugin has **zero** 16 KB exposure; the FFmpeg route required a re-uploaded 100 MB AAR (`ffmpeg_kit_flutter/CHANGELOG.md:126`).

## 4. What this means for a rebuild (brief)

1. **There is a real gap:** the incumbent has 167 k monthly downloads, an abandoned H.264-only Android dependency, no bitrate control, no HEVC, no HDR story, and 176 open issues; the two native challengers are single-maintainer, one built on raw MediaCodec (heavy to maintain), the other on Media3 but with an over-promising option surface, a possibly-unwired Android bitrate, and no background support.
2. **Stack:** Media3 Transformer (`setVideoMimeType`, `VideoEncoderSettings.setBitrate`, `Presentation`, `ClippingConfiguration`, `setHdrMode(TONE_MAP_…OPEN_GL)`, `mediaProcessing` FGS) on Android; AVAssetReader/Writer with `AVVideoAverageBitRateKey`, `.hevc` opt-in, `transform = preferredTransform`, passthrough audio with `sourceFormatHint`, tone-mapped SDR default on Apple; optional WebCodecs+Mediabunny web target. minSdk 23 (Media3 1.9+), iOS 13+ (async export) — both well above Flutter's own floors.
3. **Design the API around what the engines can actually do** (bitrate, resolution, fps cap, codec, trim, audio passthrough/strip/re-encode, cancel, progress, HDR mode, background) and report what happened (`usedCodec`, `wasTransmuxed`, `toneMapped`, `passes`) — the pattern `light_compressor_v2` gets right and `v_video_compressor` gets wrong.
4. **Budget the hard parts up front:** HDR test clips from an iPhone (Dolby Vision 8.4) and a Pixel (HLG10), portrait/rotated clips, clips with AAC vs PCM vs no audio, a 4K60 clip, and an iOS background-suspension test — these are precisely where every package above has shipped regressions.
