# Quick task 260927-r4k: Fix the Apple `awaitCompressResult` registration race

## Why

CI run 36349558026 (Phase 6 wave 1, commits `457ffd1`..`3ec3648`, which touched no native
code) failed the Apple job in a Phase 5 suite, `example/integration_test/jobs_background_test.dart`,
first case "Isolate.run: a real compression completes entirely off the root isolate":

```
CompressVideoException(unknown): awaitCompressResult called for unknown jobId "0-bae9a943cae4caf7":
startCompress was never called for it (platformDetail: unknown)
```

The same suite passed on the iOS simulator in runs 36327133883 and 36341721538, so this is a
latent race, not a regression from Phase 6 code. Root cause, read from the code:

- `lib/src/compress_job.dart` (`_run`, background-isolate branch, ~line 296-336) fires
  `startCompress(path, id, request)` WITHOUT awaiting it and immediately calls
  `awaitCompressResult(id)`. Two host calls, two channels, back to back.
- `darwin/compress_video/Sources/compress_video/Compression.swift`: Pigeon's generated setup
  wraps every handler in `Task { @MainActor in ... }` (Messages.g.swift ~lines 796-864), but
  `Compression` is a plain `final class` and both `startCompress` and `awaitCompressResult` are
  nonisolated `async` methods, so each hops OFF the main actor onto the cooperative pool the
  moment it is called. `startCompress` then runs `requireValidJobId`,
  `Arguments.requireValidCompressRequest(request)` (FileManager checks) and only THEN
  `await JobRegistry.registerJob(jobId:)` (a hop back to `@MainActor`). `awaitCompressResult`
  concurrently hops off, then `await JobRegistry.isConsumedJobId` / `isKnownJobId` hop back.
  Nothing orders `registerJob` before `isKnownJobId`; when the second task wins,
  `isKnownJobId` is false and the CR-02 guard throws "unknown jobId".
- Android has no such race: `Compression.kt`'s `startCompress` is a `suspend fun` delivered on
  the main looper and calls `JobRegistry.resultDeferredFor(jobId)` before its first suspension
  point, so registration is complete before the next channel message is handled.

## Fix (Apple side only; Android is already correct — keep parity by matching its ordering)

1. In `Compression.swift`, make registration happen BEFORE the first suspension point and on the
   main actor, exactly as Android does: mark `startCompress` `@MainActor` (Pigeon already calls
   it from a `Task { @MainActor in }`, so no extra hop), keep `requireValidJobId` +
   `requireValidCompressRequest` as they are, and call `JobRegistry.registerJob(jobId: jobId)`
   synchronously (no `await`) as the first statement after `requireValidJobId` succeeds — BEFORE
   `requireValidCompressRequest`, so even a request that fails validation is a known job whose
   failure `completeResult` records (wrap the validation in the same do/catch so its error goes
   through `completeResult` too; the guard `requireValidJobId` stays outside since an invalid id
   cannot be registered). `runCompress` is nonisolated `async` and still hops off the main actor
   when awaited, so the engine work does not move onto the main thread. Update the class doc
   comment (lines ~68-75) to say registration is synchronous on the main actor for this reason.
2. Also make `awaitCompressResult` `@MainActor` so its `isConsumedJobId`/`isKnownJobId` checks run
   in handler order on the main actor without a hop (drop the now-unnecessary `await`s on those two
   calls; `JobRegistry.awaitResult` stays awaited).
3. Belt and braces, bounded and typed: if `isKnownJobId` is still false, poll it up to 40 times
   with `try await Task.sleep(nanoseconds: 50_000_000)` (2 s total) before throwing the existing
   "unknown jobId" error, so a reordering anywhere in the messenger still resolves typed and never
   hangs. Keep the error message text unchanged. Mirror the same 2 s bounded grace in
   `Compression.kt`'s `awaitCompressResult` (`delay(50)` loop, 40 iterations) for parity, with a
   comment saying Android's ordering already makes it unreachable in practice.
4. XCTest: add a case to `example/ios/RunnerTests/RunnerTests.swift` that calls
   `awaitCompressResult` for a jobId and THEN, ~100 ms later, calls `registerJob` +
   `completeResult` for it, asserting the await resolves with the result rather than throwing
   "unknown" (proves the grace period). Copy the file byte-for-byte to
   `example/macos/RunnerTests/RunnerTests.swift` (`cmp` must succeed). Add the matching JVM test
   in `android/src/test/kotlin/.../JobRegistryTest.kt` or a `CompressionTest.kt` only if
   `Compression.kt` is testable there without an Android context; otherwise document why not in
   the SUMMARY.
5. Verification: Swift cannot be compiled on danserver. Probe the Mac ONCE with
   `timeout 15 ssh -o ConnectTimeout=8 -o BatchMode=yes dans-macbook-air true`; if reachable, run
   `bash tool/mac_sync.sh && bash tool/mac_run.sh xctest-ios` and then
   `bash tool/mac_run.sh ios integration_test/jobs_background_test.dart` (MAC_RUN_TIMEOUT=900);
   if not reachable, do not retry — CI is the verifier. Run the Android JVM tests
   (`cd android && timeout 900 ./gradlew testDebugUnitTest` or the project's documented command)
   and `flutter analyze` (flutter-stable PATH) before pushing. Push to BOTH remotes; at most 3
   pushed CI attempts. Do not poll CI: record the run id in the SUMMARY as pending and return.

## Acceptance

- `Compression.swift`: `startCompress` is `@MainActor`; `JobRegistry.registerJob(jobId: jobId)`
  is called with no `await` before `Arguments.requireValidCompressRequest`; `awaitCompressResult`
  is `@MainActor` and contains a bounded (≤ 2 s) known-id wait before throwing "unknown jobId".
- `Compression.kt`: `awaitCompressResult` contains the same bounded wait.
- `example/ios/RunnerTests/RunnerTests.swift` and `example/macos/RunnerTests/RunnerTests.swift`
  are byte-identical and contain the new grace-period case.
- No Pigeon contract change (`pigeons/messages.dart` untouched); no hand-written channels.
- CI: `jobs_background_test.dart` passes on the iOS simulator and macOS host in the pushed run.
