# Quick task 260923-9lc: Fix Apple CI simulator suite watchdog so launch hangs fail fast

## Why

Every push since 03-04 lands a failed-CI email. The failing step is the Apple job's
"Run corpus integration tests on the iOS simulator" (latest: run 35826458554, step timed out
after 60 minutes; the `parity` job then fails because `apple` failed).

Root cause, from that run's log:

- `flutter test <suite> -d <sim>` discovers the Dart VM service by tailing the simulator's
  unified log through `xcrun simctl spawn <udid> log stream` (flutter_tools
  `ios/simulators.dart`, `_IOSSimulatorLogReader`). On the hosted macOS runner that process
  dies on roughly half of all launches; the tool prints `No tests ran.` then
  `Error waiting for a debug connection: The log reader failed unexpectedly` and never exits.
  Long-standing upstream flake: flutter/flutter#116248, #77992.
- The step's watchdog was meant to kill such a launch after 150 s, but its "did the app
  launch" check was `wc -l > 1`. Flutter's own preamble (`Warning: Missing build name`,
  `Running Xcode build...`, `Xcode build done.`) pushes the log past one line instantly, so
  every hang got the 600 s post-launch budget instead. Measured: 4 hangs at ~12 min each
  (build ~1.5-2 min + 600 s + reset) = 48 of the 60 minutes.

## Tasks

1. Move the suite loop into `tool/run_ios_integration_suites.sh <udid>` (testable locally
   against a fake `flutter`) and make the watchdog phase-aware:
   - build phase: wait for `Xcode build done.` (budget 900 s);
   - launch phase: wait for a real test-progress line (`^[0-9]+:[0-9]{2} \+[0-9]+`, excluding
     the initial `: loading ` line) within 150 s;
   - run phase: 600 s to finish;
   - at any point, `Error waiting for a debug connection` or `No tests ran.` kills the attempt
     immediately (status 99 = launch failure, retried);
   - attempt cap 8 per suite (a hang now costs ~2 min, not ~12).
2. Self-test the script with a fake `flutter` covering: pass, log-reader failure then hang,
   silent launch hang, genuine test failure (fail fast, no retry).
3. Point `.github/workflows/ci.yml` at the script; keep `timeout-minutes: 60`; rewrite the
   step comment to document the upstream issue and the measured timeline. Commit, push to
   `github` (CI) and `origin`.

## Verification

- Local self-test of the script passes all four scenarios.
- `bash -n` on the script; `actionlint`-free sanity: the workflow still parses (`yq`/python).
- Next CI run on `github`: hangs show as ~2-minute warnings, step completes well under 60 min.
