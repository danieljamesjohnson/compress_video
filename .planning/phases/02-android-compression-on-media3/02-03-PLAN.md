<objective>
Turn the tracer's inline target arithmetic into one pure, tested function, and make all four ways of
asking for a size actually reach the encoder — with no upscaling, no odd dimensions, and a frame-rate
cap that a 60 fps clip can prove.

Purpose: PITFALLS.md rows 6 and 13 are two halves of the same failure. One competitor exposed bitrate
options that never reached `VideoEncoderSettings`, so file sizes did not change across "bitrates". The

unit test per rule, and by asserting on the emulator that the produced file's real dimensions,
frame rate and byte count match what the options asked for.

explicit targets, target size within tolerance, the fps cap and the no-upscale rule.

## The resolution contract this plan implements

`SizeGuard` takes the probed input facts and the request message and returns one plan. Every rule
below is a separate unit test; the order matters because later steps read earlier ones.

1. `effectiveLongSidePx` = min(`maxLongSidePx` if set else the preset's own `maxLongSidePx`, the
   input's displayed long side). Never above the input's own (D-08).
2. `scale` = `effectiveLongSidePx` divided by the input's displayed long side.
3. `targetWidthPx` and `targetHeightPx` = the input's displayed width and height multiplied by
   `scale`, each then rounded DOWN to the nearest even integer, each floored at 16.
4. `effectiveFps` = min(`maxFps`, the input's frame rate rounded half-up to the nearest integer).
   When the input's frame rate is unknown, `maxFps` is used unchanged (D-08, D-12).
5. `audioBitrateBps` = 0 when the audio is stripped; otherwise the requested value if given, else
   the input's own audio bitrate if the platform reports one, else 128000 — then clamped into the
   range 8000 to 960000, which is the emulator AAC encoder's own advertised range read live in
   02-RESEARCH.md Pitfall 11.
6. `videoBitrateBps`, in this precedence order:
   - an explicit `videoBitrateBps` is used as given;
   - else if `targetSizeMb` is set: `(targetSizeMb x 1000000 x 8 / outputDurationSeconds) x 0.97`
     minus `audioBitrateBps`, floored at 200000 — the 0.97 is the 3 percent mux overhead D-09
     names, and `outputDurationSeconds` is the trimmed duration when a trim is requested;
   - else the preset's bitrate scaled by the square of (`effectiveLongSidePx` divided by the
     preset's own `maxLongSidePx`) and by (`effectiveFps` divided by 30), floored at 200000.
   Then, in every branch, capped at the input's own video bitrate when the platform reports one, so
   a re-encode can never ask for more bits than arrived.
7. `predictedOutputBytes` = ((`videoBitrateBps` + `audioBitrateBps`) x `outputDurationSeconds` / 8)
   multiplied by 1.03 for container overhead, rounded up.

Megabytes here are decimal (1,000,000 bytes), matching how every upload limit and every carrier data
allowance is stated; say so in the `targetSizeMb` dartdoc so nobody has to guess between 10^6 and 2^20.

The transmux and never-larger predicates that also live on this function are added in plan 02-04;
this plan builds the arithmetic they will read.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| caller -> plugin (sizing options) | Caller-supplied numbers become encoder configuration and a bitmap-sized encode |
| Dart -> native channel | An external caller can reach the generated host API directly and skip the Dart-side validation |
| plugin -> platform encoder | Resolved dimensions and bitrates are handed to `MediaCodec` through Media3's encoder factory |
