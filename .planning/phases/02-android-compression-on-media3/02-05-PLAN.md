<objective>
Finish the parts of the output a user actually sees and hears: the track that comes out of the audio
pipeline, and the fact that a phone-shot portrait video plays the right way up with no bars down the
sides.

Purpose: three separate competitors shipped audio bugs — one re-encodes to AAC unconditionally and
never passes through, one crashes on real devices when passthrough is attempted without a format
hint, and the incumbent fails outright on unusual channel counts. The orientation bug class is worse
because it is silent: PITFALLS.md row 9 records inverted width and height swaps, lost transforms and
metadata-only rotations, all of which produce a file that looks fine in the developer's player and
sideways in the user's. Both are closed the same way — let the platform do the work, then assert what
actually came out of it by sampling pixels of the produced file.
Output: all three audio modes working and reported honestly, upright output proven by pixel probe,
no letterboxing proven by edge probe, and trim implemented with a duration assertion.
</objective>

## Flagged assumption — unresolved probe edge (AUDO-01)

The deterministic edge probe classified AUDO-01's edge as `unclassified`; it is deliberately NOT
auto-resolved. The assumption this plan proceeds on: **"MP4-compatible AAC" means the source audio
track's normalised codec token is the AAC token and the exporter's own audio conversion-process field
reports a copy.** If a device exists that reports an AAC track which the muxer then refuses to copy,
this definition is too loose and passthrough needs a profile check as well. Surface it to the
developer at verification; do not close it by fiat.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| caller -> plugin (audio options) | Caller-supplied bitrate and channel count become encoder and audio-processor configuration |
| source audio track -> platform encoder | An arbitrary source audio track is fed through the platform's decoder, mixer and encoder |
| caller -> plugin (trim range) | Caller-supplied millisecond positions become a clipping configuration on the media item |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-17 | Denial of Service | An out-of-range audio bitrate reaching the AAC encoder and failing initialisation | medium | mitigate | `SizeGuard` clamps the resolved audio bitrate into the 8000 to 960000 range the device encoder advertises before it reaches the encoder settings, and non-positive values are rejected at validation on both sides of the channel; unit cases cover both bounds |
| T-02-18 | Denial of Service | An unusual source audio track (unexpected channel count, unexpected sample format) crashing the pipeline | high | mitigate | Channel changes go through the platform's own mixing processor rather than hand-written sample maths, a non-AAC source falls back to a re-encode rather than an assumed copy, and any track the platform refuses arrives as a typed `unsupportedInput` through the export error callback rather than as a native crash |
| T-02-19 | Repudiation | `audioReencoded` not describing the produced file | high | mitigate | The flag is read from the export result's own audio conversion-process field and `audioCodec` from a re-probe of the finished file, never from the request; the prohibition in this plan's `must_haves` states the rule and integration cases assert both directions |
| T-02-20 | Tampering | A trim range that is inverted, negative or beyond the clip | medium | mitigate | `CompressOptions.validate()` and the native `Arguments` mirror both reject a negative start and an end not strictly greater than the start before the channel is touched; the platform clipping configuration clamps a range beyond the clip's own duration rather than failing |
</threat_model>
