## Contract decisions this plan fixes (record them in the SUMMARY)

- **Two host APIs, not one.** `pigeons/messages.dart` declares `ProbeHostApi` (media info) and
  `ThumbnailHostApi` (thumbnails) as separate `@HostApi()` classes. This is the discretionary
  choice CONTEXT.md leaves open on generator shape, and it is what lets the Android probe land
  here while the thumbnail implementation lands in plan 01-05 and the Apple implementations of
  both land in 01-06 — with no unimplemented interface members anywhere in between. Later phases
  add `CompressionHostApi` and `JobHostApi` the same way.
- **`getThumbnail` returns `Uint8List`, `getThumbnailFile` returns a `String` path.** CONTEXT.md's
  model-types bullet mentions a `Thumbnail` type in passing, and its return-type bullet fixes the
  concrete return values. The return-type bullet is the operative one: no wrapper class is
  introduced for thumbnails. This is stated here so the omission is visible rather than silent.
- **Cross-platform-identical versus tolerant fields.** `durationMs` (within one frame), `widthPx`,
  `heightPx`, `rotationDegrees`, `sizeBytes`, `hasAudio`, `isHdr` and the normalised `videoCodec`
  token must be identical on every platform. `videoBitrateBps` and `frameRateFps` are
  platform-reported and carry explicit tolerances in the sidecar. This is what makes success
  criterion 1 ("the values match on the Android emulator and the iOS simulator") testable.
- **`videoCodec` is a normalised token**, one of `h264`, `hevc`, `av1`, `vp9`, `unknown`. Android's
  `video/avc` and Apple's `avc1` both normalise to `h264`. The raw platform string is not exposed.
- **`isHdr` only.** `MediaInfo` exposes `isHdr` and no `hdrFormat` enum in this phase, which
  CONTEXT.md explicitly permits. Detection that is unavailable on the running OS version yields
  `false`, never an exception.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| caller → plugin | A file path supplied by the host app crosses into the plugin and reaches native file APIs |
| plugin → platform media parser | Untrusted media bytes are handed to `MediaMetadataRetriever`, an OS-level parser with a long CVE history |
| plugin → platform log | Anything written to logcat is readable by other tooling on the device during development |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-08 | Tampering | `path` argument reaching `MediaMetadataRetriever.setDataSource` | medium | mitigate | `Arguments.kt` rejects blank paths, canonicalises the path before use, and requires an existing readable regular file. The plugin runs inside the host app's own sandbox, so this cannot grant access the caller did not already have; the control exists to turn a traversal attempt into a typed `fileNotFound` instead of an unexpected native failure |
| T-01-09 | Denial of Service | Malformed or corrupt media crashing the native parser | high | mitigate | Every retriever and extractor call is wrapped so that a parser failure becomes `unsupportedInput` or `io` and the retriever is released in a `finally`. Success criterion 3 and CORE-04 both require that no failure crashes the host app; the corpus error cases (missing file, zero-byte file, non-video file) are integration-tested |
| T-01-10 | Information Disclosure | Platform logging of paths or metadata | medium | mitigate | No `android.util.Log` or `println` call exists in any plugin Kotlin source, asserted by a grep gate in this plan's acceptance criteria. Failure detail travels back to the caller in `platformDetail`, where the app decides what to do with it |
| T-01-22 | Information Disclosure | Untrusted media parsed by an OS media parser (CVE surface inherent to `MediaMetadataRetriever`) | medium | transfer | Out of this plugin's control: the parser belongs to the platform. Transferred to the OS vendor, mitigated only by the project's standing commitment to current minSdk/toolchain and by not disabling any OS-level hardening |
