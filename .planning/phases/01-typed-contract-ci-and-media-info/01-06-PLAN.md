## Apple facts and flagged assumptions carried in from research

- `AVAssetImageGenerator.appliesPreferredTrackTransform` **defaults to `false`**. Research recorded
  this as CITED rather than VERIFIED (no Mac was available), with an explicit instruction to
  re-check it on the first Apple CI run. Setting it to `true` is harmless if the default were ever
  different; leaving it unset is the sideways-thumbnail bug every competitor shipped.
- Sources conflicted on whether the awaited `AVAssetTrack.load(_:)` property API requires iOS 15 or
  iOS 16 / macOS 13. It does not change what must be written: the plugin targets iOS 13 and macOS
  11, so a completion-handler fallback is required either way. Gate the modern path with an
  availability check and keep the fallback.
- The iOS and macOS Flutter registrars differ: one exposes the binary messenger as a method and the
  other as a property. This is the single genuinely platform-specific line in the plugin and must
  sit behind a compile-time platform branch.
- New Swift files added under `darwin/compress_video/Sources/compress_video/` are picked up
  automatically by the podspec glob and by the Swift Package target directory — no Xcode project
  edit is needed. New files added to a **RunnerTests** target would need a project edit, so all
  XCTest code must live inside the two existing `RunnerTests.swift` files.
- Apple's `AVAssetTrack` exposes `estimatedDataRate` (bits per second) and `nominalFrameRate`;
  either can legitimately be `0`, which must map to `null`, never to a reported zero.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| caller → plugin | A file path and an optional output path supplied by the host app reach Apple file APIs |
| plugin → AVFoundation | Untrusted media bytes are handed to an OS media parser |
| plugin → macOS sandbox | On macOS the host app may be sandboxed, so an arbitrary destination path may simply not be writable |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-14 | Tampering | `path` and `outputPath` reaching `AVURLAsset` and the file manager | medium | mitigate | `Arguments.swift` standardises both paths, requires an existing readable regular file for the input, and requires an existing writable parent directory for the output before any bytes are produced. Both are bounded by the host app's own sandbox; the control converts a traversal attempt into a typed error rather than an unexpected native failure |
| T-01-15 | Denial of Service | Force-unwrapped AVFoundation optionals crashing the host app | high | mitigate | No force-try, force-cast, force-unwrap or `fatalError` appears in any Swift source, asserted by a grep gate in this plan's acceptance criteria, and every load status is checked before the value is read. This is the exact crash the incumbent shipped on iOS (unchecked exporter status, 19 reactions) |
| T-01-16 | Information Disclosure | Writing outside the app container on macOS | medium | mitigate | The default destination is the user caches directory obtained from the file manager, which resolves inside the app container for a sandboxed app. An explicit `outputPath` that the sandbox refuses surfaces as the `io` reason rather than as a crash |
| T-01-24 | Information Disclosure | Apple platform logging of paths or metadata | medium | mitigate | No `NSLog` or `print` call exists in any plugin Swift source, asserted by a grep gate. Failure detail travels back to the caller in the error's details field |
</threat_model>
