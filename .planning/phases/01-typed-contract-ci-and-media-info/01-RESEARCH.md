## User Constraints (from CONTEXT.md)

### Locked Decisions

**Dart API surface (info + thumbnails)**
- Entry point is a `CompressVideo` class with a `const CompressVideo()` constructor and an
  optional `BinaryMessenger` parameter (for background isolates in Phase 5). No static singleton,
  no global state. Methods in this phase: `getMediaInfo(String path)`, `getThumbnail(String path,
  {int positionMs = 0, int quality = 80, int? maxDimensionPx})` and `getThumbnailFile(... ,
  {String? outputPath})`. Verb names deliberately echo `video_compress` for migrants.
- Public model types (`MediaInfo`, `Thumbnail`/thumbnail file result) are hand-written immutable
  Dart classes with dartdoc on every field, mapped from the Pigeon-generated classes. Generated
  classes stay private in `lib/src/messages.g.dart`.
- `getThumbnail` returns `Uint8List` JPEG bytes. `getThumbnailFile` writes a JPEG with a unique
  name in the app cache directory (or at `outputPath` if given) and returns its path.
  `quality` is 1-100 JPEG quality; `maxDimensionPx` caps the longer side, never upscales.
- Failures complete the Future with a typed `CompressVideoException` carrying a `reason` enum
  (at least `fileNotFound`, `unsupportedInput`, `decoderUnavailable`, `io`, `cancelled`,
  `unknown` — later phases add `encoderUnavailable`, `outOfSpace`, `interrupted`), a
  human-readable `message` and an optional `platformDetail` string. No call ever resolves to
  `null`; a raw `PlatformException` never escapes the public API.

**Pigeon contract conventions**
- Every numeric quantity crossing the channel has its unit in the field name: `durationMs`,
  `positionMs`, `sizeBytes`, `widthPx`, `heightPx`, `videoBitrateBps`, `frameRateFps`,
  `rotationDegrees`. Width/height describe the **displayed** (rotation-corrected) orientation.
  Every field has a dartdoc line stating the unit and the sentinel for unknown (nullable, not 0).
- Single source of truth `pigeons/messages.dart`. Generated outputs: `lib/src/messages.g.dart`,
  Kotlin under `android/src/main/kotlin/com/danjjohnson/compress_video/Messages.g.kt`, Swift in
  the shared `darwin/` tree. Android namespace `com.danjjohnson.compress_video`. A CI step
  regenerates and fails on any diff. Pigeon version pinned in `dev_dependencies`.
- Error transport: native code throws `FlutterError(code: <reason enum name>, message, details)`;
  the Dart wrapper maps `PlatformException.code` to `CompressVideoException.reason`, falling back
  to `unknown` with the original code preserved in `platformDetail`. Success replies contain only
  success data.
- All host methods are `@async`. Native work (metadata read, frame decode, JPEG encode) runs off
  the main/platform thread (Kotlin executor or coroutine; Swift `DispatchQueue`) and replies on
  the platform thread. This is the shape later compression jobs will reuse.

**Repository layout, Apple packaging, corpus**
- Plugin lives at the repository root (pub-ready `pubspec.yaml`), with `example/`, `pigeons/`,
  `test/`, `example/integration_test/`, and `corpus/`. `corpus/` and `.planning/` are excluded
  from the published package via `.pubignore`. Corpus clips are committed directly (each under
  ~2 MB); no git LFS.
- Apple code lives once in `darwin/` using Flutter's `sharedDarwinSource: true` for both `ios`
  and `macos` in the pubspec plugin block, with one podspec and one `Package.swift` so both
  CocoaPods and Swift Package Manager install from the same sources.
- Phase 1 corpus is generated by ffmpeg on danserver to mirror phone output structurally:
  (a) `portrait_rot90.mp4` — frames encoded 1920×1080 with a 90° display matrix (as phones do),
  H.264 + AAC stereo, ~4 s, moving pattern with a burnt-in millisecond timecode so a thumbnail at
  1500 ms is visually checkable; (b) `small_480p.mp4` — an already-small, low-bitrate clip;
  (c) `noaudio_720p.mp4` — no audio track. Each clip ships with a sidecar `*.expected.json`
  holding the ground-truth `MediaInfo` values produced by ffprobe, which the integration tests
  assert against.
- Local Android toolchain on danserver: `openjdk-17-jdk-headless` via apt (passwordless sudo),
  Android cmdline-tools into `~/Android/Sdk` with `platform-tools`, `platforms;android-36`,
  matching `build-tools`, `emulator`, and one `system-images;android-35;google_apis;x86_64`
  image (fallback to 36 if 35 is unavailable). `ANDROID_HOME`/`ANDROID_SDK_ROOT` exported from
  `~/.profile` and `~/.bashrc`, plus `flutter config --android-sdk`. Emulator runs headless
  (`-no-window -gpu swiftshader_indirect -no-audio -no-boot-anim`) with KVM. Record every install
  step in the project `.claude/CLAUDE.md` lane notes so the next agent does not re-derive it.

## Summary

This phase is pure plumbing plus two read-only native calls, and every version pin required by
`STACK.md`'s "verify at Phase 1" list was checked live today against an authoritative source: the
**current Flutter 3.44.1 plugin template** (inspected directly by running `flutter create`),
**Pigeon 29.0.1** (pub.dev, verified-publisher `flutter.dev`, published 3 days ago), **media3
1.11.0** (still current per developer.android.com), **AGP 9.0.1 / Kotlin 2.3.20 / Gradle
(bundled) / compileSdk 36 / JVM 17** (all read directly out of the generated
`android/build.gradle.kts`), **flutter_lints 6.0.0**, and the GitHub Actions toolchain
(`subosito/flutter-action@v2`, `reactivecircus/android-emulator-runner@v2`, `macos-latest` =
macOS 26 Tahoe with Xcode 26.6 and CocoaPods 1.17.0 preinstalled).

The single most important structural finding is that the current Flutter plugin template does
**not** generate a shared `darwin/` tree by default — `flutter create --platforms=android,ios,macos`
produces separate `ios/<pkg>/Package.swift` and `macos/<pkg>/Package.swift`. The
`sharedDarwinSource: true` pattern CONTEXT.md requires is real and shipping (Flutter's own
`shared_preferences_foundation` plugin uses it), but it must be **built by hand**: move both
platforms' native code into one `darwin/<pkg>.podspec` + `darwin/<pkg>/Package.swift` +
`darwin/<pkg>/Sources/<pkg>/` tree, with `s.ios.dependency`/`s.osx.dependency` split in the one
podspec and `.iOS("13.0"), .macOS("10.15")` in the one `Package.swift`. The exact layout is
captured verbatim below from Flutter's own source (Sources section, tagged VERIFIED).

The second major finding is a **live, reproducible bug in the corpus-generation plan**: the ffmpeg
installed on danserver (6.1.1-3ubuntu5) prints a "converting rotate metadata to display matrix"
deprecation notice but **does not actually write the display matrix** — verified by generating a
clip, remuxing with `-metadata:s:v:0 rotate=90`, and parsing the raw `tkhd` box, which came back
as the identity matrix. `-display_rotation` is similarly a dead end (it is an *input*-side option
in this build, not an output-writing one). The fix, verified end-to-end this session, is to encode
the plain landscape clip and then patch the `tkhd` matrix directly with a ~20-line Python script
(exact byte layout and rotation values below); `ffprobe` then correctly reports
`side_data_list: [{"side_data_type": "Display Matrix", "rotation": -90}]`, matching real iPhone
portrait output.

The third finding worth flagging early: `AVAssetImageGenerator.appliesPreferredTrackTransform`
**defaults to `false`**, not `true` (confirmed against Apple's own doc page after a first-pass
summary claimed the opposite) — this is exactly PITFALLS.md #9's rotation bug class, and every
competitor in the brief has shipped a variant of it. The plan must explicitly set it `true`.

**Primary recommendation:** Build the Pigeon contract exactly as CONTEXT.md specifies (it matches
Pigeon 29.0.1's real, verified options), hand-assemble the `darwin/` shared-source tree using the
`shared_preferences_foundation` layout as the template, generate the corpus with ffmpeg's
lavfi/drawtext pipeline plus the verified tkhd-matrix patch script (not the `-metadata:s:v:0
rotate=` trick, which is a no-op on this box), and wire CI exactly as CONTEXT.md specifies — every
action/tool named there is current and does what CONTEXT.md assumes.

## Architectural Responsibility Map

| Capability | Primary Tier | Secondary Tier | Rationale |
|------------|-------------|----------------|-----------|
| Typed request/response contract (Pigeon) | Cross-cutting (codegen) | Dart public API | Pigeon generates into both the Dart and native tiers from one source of truth; it is not owned by either at runtime |
| Media info probing | Native platform (Android: `MediaMetadataRetriever`; Apple: `AVAssetTrack`) | — | Requires OS media frameworks; no cross-platform Dart implementation exists or should exist |
| Thumbnail generation | Native platform (Android: `MediaMetadataRetriever`/`getScaledFrameAtTime`; Apple: `AVAssetImageGenerator`) | — | Same as above; JPEG encode also happens natively (`Bitmap.compress` / `UIImage`+`NSBitmapImageRep`) to avoid shipping a second image codec in Dart |
| Public Dart API surface (`CompressVideo`, `MediaInfo`, exceptions) | Dart (`lib/`) | — | Owns documentation, stability, and the hand-written model classes that wrap generated Pigeon types |
| Error typing/translation | Native (throws `FlutterError`) + Dart (catches `PlatformException`, maps to `CompressVideoException`) | — | Both tiers cooperate: native produces the typed code, Dart is the only place a raw platform exception is allowed to be caught |
| CI build/test orchestration | CI (GitHub Actions) | — | Not part of the shipped plugin; verifies the other four rows on every push |
| Corpus generation | Dev tooling (ffmpeg script, checked in) | — | Produces fixtures consumed by the Native platform tier's integration tests; not part of the plugin runtime |

### Pattern 1: Shared Darwin source (`sharedDarwinSource: true`)
**What:** One `darwin/` directory holds all Swift source, one podspec, one `Package.swift`,
serving both `ios` and `macos` platform entries in `pubspec.yaml`.
**When to use:** Any plugin whose iOS and macOS implementations share the same Swift code (true
here — `AVFoundation` is nearly identical on both).
**Example (verified from Flutter's own `shared_preferences_foundation` plugin, read live via
`gh api repos/flutter/packages/contents/...` on 2026-09-15):**

`pubspec.yaml`:
```yaml
# Source: github.com/flutter/packages, packages/shared_preferences/shared_preferences_foundation/pubspec.yaml
flutter:
  plugin:
    platforms:
      ios:
        pluginClass: SharedPreferencesPlugin
        sharedDarwinSource: true
      macos:
        pluginClass: SharedPreferencesPlugin
        sharedDarwinSource: true
```

`darwin/shared_preferences_foundation.podspec` (one podspec, `s.ios.*`/`s.osx.*` split):
```ruby
# Source: same repo, darwin/shared_preferences_foundation.podspec
Pod::Spec.new do |s|
  s.name             = 'shared_preferences_foundation'
  s.source_files = 'shared_preferences_foundation/Sources/shared_preferences_foundation/**/*.swift'
  s.ios.dependency 'Flutter'
  s.osx.dependency 'FlutterMacOS'
  s.ios.deployment_target = '13.0'
  s.osx.deployment_target = '10.15'
  s.pod_target_xcconfig = { 'DEFINES_MODULE' => 'YES' }
  s.swift_version = '5.0'
end
```

`darwin/shared_preferences_foundation/Package.swift` (one Package.swift, both platforms):
```swift
// Source: same repo, darwin/shared_preferences_foundation/Package.swift
let package = Package(
  name: "shared_preferences_foundation",
  platforms: [ .iOS("13.0"), .macOS("10.15") ],
  products: [ .library(name: "shared-preferences-foundation", targets: ["shared_preferences_foundation"]) ],
  targets: [ .target(name: "shared_preferences_foundation", dependencies: []) ]
)
```

### Anti-Patterns to Avoid
- **Trusting `-metadata:s:v:0 rotate=` on this box's ffmpeg:** it prints a "converting to display
  matrix" deprecation notice but does not write one (verified: raw `tkhd` box came back identity
  after applying it, both on re-encode and on `-c copy` remux). Use the direct matrix patch
  instead (Code Examples).
- **Leaving `appliesPreferredTrackTransform` at its default:** the default is `false`, not `true`
  — every rotated thumbnail will come back sideways unless this is set explicitly.
- **Reading Android HDR/color keys without an SDK_INT guard:** `METADATA_KEY_COLOR_TRANSFER` /
  `METADATA_KEY_COLOR_STANDARD` / `METADATA_KEY_COLOR_RANGE` were added in a later API level than
  this project's minSdk 23 (see Open Questions) — calling them on an old device without a guard
  either returns null or, on `MediaFormat`, throws.
- **Publishing `corpus/` inside the pub.dev package:** `.pubignore`, not `.gitignore`, controls
  what `dart pub publish` uploads, and — critically — **a directory with both files ignores its
  own `.gitignore`, using only `.pubignore`**. `[CITED: dart.dev/tools/pub/publishing]` So
  `corpus/` needs an explicit `.pubignore` entry even though it should stay tracked in git.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Cross-language typed messages | A hand-written `MethodChannel` + `Map<String,dynamic>` protocol | Pigeon 29.0.1 | This is the exact bug class (three different units for "position") that sank the incumbent; Pigeon generates typed getters/setters and typed errors from one source file |
| Rotation-correct thumbnail | Manual bitmap rotation math from `METADATA_KEY_ROTATION`/`preferredTransform` | `getScaledFrameAtTime` (Android, which already applies rotation to the output bitmap) / `AVAssetImageGenerator` with `appliesPreferredTrackTransform = true` (Apple) | Both platform APIs already do the rotation; hand-rolling it is exactly how PITFALLS.md #9's black-bars/sideways bugs happen |
| MP4 rotation matrix construction for the corpus | A generic "MP4 metadata editor" dependency | ~20-line direct `tkhd`-box patch (Code Examples) — box format is public (ISO/IEC 14496-12) and was validated end-to-end this session | No new dependency, and the well-known ffmpeg metadata shortcut is verified broken on this box anyway |
| Error taxonomy translation | Ad-hoc `try/catch` per call site in Dart | One central `PlatformException.code → CompressVideoException.reason` mapping function, exercised by a unit test per reason | Matches CONTEXT.md's decision and keeps the reason enum the single source of truth as later phases add reasons |

**Key insight:** Every "hand-roll" temptation in this phase (rotation math, MP4 metadata editing,
channel protocol) maps directly to a documented incumbent bug in PITFALLS.md. The native SDKs and
Pigeon already solve all of them; the work is wiring, not invention.

## Common Pitfalls

### Pitfall 1: ffmpeg's `rotate=` metadata trick is a silent no-op on this box
**What goes wrong:** `ffmpeg -metadata:s:v:0 rotate=90 -c copy out.mp4` prints "Conversion of a
'rotate' metadata key to a proper display matrix rotation is deprecated. See -display_rotation
for setting rotation instead." and appears to succeed, but the output file's `tkhd` matrix is
untouched (identity), on ffmpeg 6.1.1-3ubuntu5 as installed on danserver.
**Why it happens:** unclear (possibly a packaging-specific regression); confirmed reproducible
across both re-encode and stream-copy remux paths.
**How to avoid:** patch the `tkhd` matrix directly after encoding (Code Examples) — verified this
session to produce `ffprobe`-visible `side_data_list: [{"side_data_type": "Display Matrix",
"rotation": -90}]`, matching real iPhone portrait output.
**Warning signs:** the corpus generation script "succeeds" but the sidecar `.expected.json`'s
rotation assertion is trivially true because ffprobe reports no side data on either side.
`[VERIFIED: reproduced live this session, raw box parse shown, fix validated round-trip]`

### Pitfall 2: `-display_rotation` is not the output-writing flag it sounds like
**What goes wrong:** `-display_rotation 90` placed as an output option errors ("input option
applied to output file"); placed as an input option before `-i`, it is silently accepted but
produces no side data either.
**Why it happens:** in this ffmpeg build, `-display_rotation` is classified as an input-side
option (it forces how ffmpeg *interprets* an existing rotation when decoding/transcoding), not an
output-writing directive.
**How to avoid:** don't rely on it for fresh corpus generation; use the direct matrix patch.
**Warning signs:** `ffmpeg -h full 2>&1 | grep display_rotation` shows the flag exists, which
looks like confirmation it will work — it does not on its own.
`[VERIFIED: reproduced live this session]`

### Pitfall 3: `AVAssetImageGenerator.appliesPreferredTrackTransform` defaults to `false`
**What goes wrong:** thumbnails from rotated (portrait) source video come back sideways because
the generator ignores the track's `preferredTransform` unless told to apply it.
**Why it happens:** the property's documented default is `false`, contrary to what a naive read
of "why would you ever want the wrong orientation" suggests.
**How to avoid:** set `imageGenerator.appliesPreferredTrackTransform = true` explicitly, and add a
corpus assertion (the portrait clip's thumbnail pixel-sampling check, per CONTEXT.md's specifics)
that would fail if this is ever reverted.
**Warning signs:** thumbnails pass on landscape corpus clips but fail (sideways) only on
`portrait_rot90.mp4`.
`[CITED: developer.apple.com/documentation/avfoundation/avassetimagegenerator/appliespreferredtracktransform
— confirmed via WebSearch cross-check after an initial WebFetch summary incorrectly stated the
default was `true`; treat this specific fact as CITED not VERIFIED since no Mac was available to
compile-check this session — flag for a fast re-check on first Apple CI run]`

### Pitfall 4: Android color/HDR metadata keys may not exist at minSdk 23
**What goes wrong:** `retriever.extractMetadata(MediaMetadataRetriever.METADATA_KEY_COLOR_TRANSFER)`
either returns `null` (safe) or, if read via `MediaExtractor`/`MediaFormat.getInteger(KEY_COLOR_TRANSFER)`
on an unsupported OS version, throws.
**Why it happens:** these keys were added well after API 23 (secondary sources place them around
API 24/29 for different retrieval paths — see Open Questions, not independently confirmed against
the primary `frameworks/base` source this session).
**How to avoid:** wrap every color/HDR key read in a try/catch and an `if (Build.VERSION.SDK_INT
>= X)` guard; treat "unavailable" as `isHdr = false` (a safe default, not a crash) rather than
propagating an exception.
**Warning signs:** `getMediaInfo` crashes only on the corpus test running against an older
emulator image, not on a modern one.
`[CITED: developer.android.com/reference/android/media/MediaMetadataRetriever +
WebSearch-aggregated MediaFormat docs; API-level claim not independently confirmed against
`frameworks/base` source — see Open Questions]`

### Pitfall 5 (from PITFALLS.md #7, #21): unit/filename bugs the incumbent shipped
**What goes wrong:** thumbnail `position` meant three different units on three platforms in
`video_compress`; thumbnail filenames collided.
**Why it happens:** untyped channel, no single source of truth for units.
**How to avoid:** already structurally prevented by the Pigeon field-naming convention
(`positionMs` everywhere) and by generating thumbnail filenames from a UUID/timestamp, not from
the source filename alone.
**Warning signs:** N/A if the Pigeon contract is followed; this is a regression check, not a new
discovery.

### Pitfall 6: `.pubignore` fully replaces `.gitignore` in any directory that has both
**What goes wrong:** if `corpus/.gitignore` is ever added (e.g. to keep large regenerated test
files out of git while iterating locally) *and* `.pubignore` also exists at the root, the
directory's `.gitignore` is ignored entirely for publish-file-list purposes.
**Why it happens:** documented `dart pub publish` behavior.
**How to avoid:** put every publish-exclusion (`corpus/`, `.planning/`) in one root `.pubignore`,
and don't rely on `.gitignore` for anything publish-related.
**Warning signs:** `dart pub publish --dry-run` lists files that were supposed to be excluded.
`[CITED: dart.dev/tools/pub/publishing, via WebSearch synthesis of the official page]`

## Code Examples

### Corpus: tkhd rotation-matrix patch (verified working, ffmpeg 6.1.1-3ubuntu5)
```python
# Source: written and round-trip-verified this session (2026-09-15) against
# ffprobe's side_data_list output. Values are the ISO/IEC 14496-12 tkhd matrix
# for a 90-degree clockwise "phone portrait" rotation (iPhone-style).
import struct

def patch_rotation(path: str, height: int, degrees_cw: int = 90) -> None:
    with open(path, 'rb') as f:
        data = bytearray(f.read())

    def find_tkhd_matrix_offset(data, start=0, end=None):
        end = end or len(data)
        i = start
        while i < end - 8:
            size = struct.unpack('>I', data[i:i+4])[0]
            boxtype = data[i+4:i+8]
            if size < 8:
                break
            if boxtype == b'tkhd':
                body_off = i + 8
                return body_off + (size - 8 - 8 - 36)  # matrix is the 36 bytes before width/height
            if boxtype in (b'moov', b'trak', b'mdia', b'udta'):
                r = find_tkhd_matrix_offset(data, i + 8, i + size)
                if r:
                    return r
            i += size
        return None

    off = find_tkhd_matrix_offset(data)
    if off is None:
        raise RuntimeError(f'tkhd box not found in {path}')

    if degrees_cw == 90:
        # verified: ffprobe then reports side_data_type "Display Matrix", rotation: -90
        vals = (0, 0x10000, 0, -0x10000, 0, 0, height << 16, 0, 0x40000000)
    elif degrees_cw == 0:
        vals = (0x10000, 0, 0, 0, 0x10000, 0, 0, 0, 0x40000000)  # identity
    else:
        raise NotImplementedError('only 0/90 derived and verified this session')

    data[off:off+36] = struct.pack('>9i', *vals)
    with open(path, 'wb') as f:
        f.write(data)
```
`[VERIFIED: ran this exact logic against a real ffmpeg-produced mp4 this session; ffprobe -show_streams
confirmed side_data_list = [{'side_data_type': 'Display Matrix', 'displaymatrix': '... -65536 ... 70778880 ... 1073741824', 'rotation': -90}]]`

## Security Domain

### Applicable ASVS Categories

| ASVS Category | Applies | Standard Control |
|---------------|---------|-------------------|
| V2 Authentication | No | No auth surface in this phase |
| V3 Session Management | No | N/A |
| V4 Access Control | No | N/A |

Missing/non-video files must produce a typed `fileNotFound`/`unsupportedInput` error (already a locked decision), not an unguarded native crash. |
| V6 Cryptography | No | No crypto in this phase |

### Known Threat Patterns for this stack

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|----------------------|
| Path traversal via a caller-supplied `outputPath` (e.g. `../../etc/...`) | Tampering | Resolve to a canonical absolute path and confirm it is within an app-controlled directory (cache dir or an explicitly app-sandboxed location) before writing; this is a natural fit for the `io` reason code already in the exception taxonomy |
| Malformed/corrupt video file crashing the native decoder | Denial of Service (local) | `MediaMetadataRetriever`/`AVAssetReader` failure states must be caught and mapped to `unsupportedInput`/`io`, never allowed to propagate as an unhandled native exception — directly required by success criterion 3 and PITFALLS.md #3/#4 |
| Untrusted file content interpreted by a native media parser (CVE surface inherent to `MediaMetadataRetriever`/`AVAssetReader`, not this plugin's code) | Tampering / Info Disclosure | Out of this plugin's control (OS-level parser); mitigated only by staying on current OS/media3 versions (already the project's stated goal) — no additional Phase 1 action beyond not disabling any OS-level hardening |
