## Facts this plan depends on (verified 2026-09-15, do not re-derive)

- ffmpeg/ffprobe 6.1.1-3ubuntu5 are installed; `drawtext` and `drawbox` filters are both present;
  `/usr/share/fonts/truetype/dejavu/DejaVuSans-Bold.ttf` exists.
- `ffmpeg -metadata:s:v:0 rotate=90` prints a deprecation notice and **writes nothing** on this
  build — the `tkhd` matrix stays identity. `-display_rotation` is an input-side option here and is
  also a dead end. Both were reproduced live during research; the working fix is the direct `tkhd`
  patch whose exact byte layout and matrix values are in RESEARCH.md → Code Examples.
- ffprobe reports the display matrix as **signed counter-clockwise** (`rotation: -90`); Android and
  Apple report **unsigned clockwise** (`90`). The sidecars must carry the platform-facing value.
- ffmpeg auto-applies the display matrix on decode (`-autorotate` defaults to on), so
  `ffmpeg -ss <t> -i portrait_rot90.mp4 -frames:v 1 ...` already yields the upright 1080x1920 frame.

    Write `corpus/verify_corpus.sh` (`set -euo pipefail`) as the single producer of the sidecars: for each committed clip it runs `ffprobe -v quiet -print_format json -show_streams -show_format`, derives the sidecar content, and in `--write` mode writes `<clip>.expected.json` while in default mode it diffs the derived content against the committed file and exits non-zero on any difference. Sidecars are never hand-edited; this script is what proves that.
    Sidecar shape — a JSON object with three blocks. `crossPlatform`: `durationMs` (integer milliseconds, rounded half-up from ffprobe's `format.duration` seconds, with a documented `durationToleranceMs` of 34 = one frame at 30 fps), `widthPx` and `heightPx` as the **displayed** dimensions (so 1080 and 1920 for the portrait clip, 854 and 480 for the small clip, 1280 and 720 for the no-audio clip), `rotationDegrees` as **unsigned clockwise** degrees (90 for the portrait clip, 0 for the other two — never ffprobe's `-90`), `sizeBytes` from the filesystem, `hasAudio`, `isHdr` (false for all three; these are 8-bit BT.709 clips), and `videoCodec` as the normalised token `h264` (the contract's normalised token set is `h264`, `hevc`, `av1`, `vp9`, `unknown` — Android's `video/avc` and Apple's `avc1` both normalise to `h264`). `tolerant`: `videoBitrateBps` with `videoBitrateTolerancePct` 25, and `frameRateFps` with `frameRateToleranceFps` 0.5 — these are the two fields platforms are allowed to disagree on, and a platform that cannot report them at all must report `null`, never `0`. `thumbnailProbe` (portrait clip only): `positionMs` 1500, `patchXPx` / `patchYPx` giving the **displayed** centre coordinates of the 200x200 colour patch, `expectedRgb` as a three-element array, and `rgbTolerance` 24 to absorb JPEG loss.

It must not create `example/` itself and must not swallow the missing-directory case.

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-04 | Denial of Service | `generate_corpus.sh` / `verify_corpus.sh` invoking ffmpeg and ffprobe | low | accept | These scripts run only on locally generated, trusted input on the developer's own machine, never on caller-supplied media. | T-01-05 | Tampering | `*.expected.json` sidecars becoming wrong-but-green | high | mitigate | `verify_corpus.sh` is the single producer of sidecar content and is run in CI; a hand-edited sidecar that no longer matches ffprobe's reading of the committed clip fails the build. | T-01-20 | Tampering | `patch_rotation.py` writing raw bytes into an MP4 | low | mitigate | The patcher raises on a missing `tkhd` box instead of writing at a guessed offset, and `generate_corpus.sh` re-reads the patched file with ffprobe and fails if the display matrix is not present with rotation -90 |
</threat_model>
