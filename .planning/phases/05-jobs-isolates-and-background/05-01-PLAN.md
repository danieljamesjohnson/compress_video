<objective>
Give `CompressVideo` a Dart-side FIFO job queue with a concurrency limit, so an app can submit
several compressions at once and get sequential, well-behaved execution with per-job progress —
without the native engines learning anything about queues.

Purpose: JOBS-03 is the requirement that makes this package usable for batch upload flows, and it
is the requirement the incumbent failed hardest (a single global `compressProgress$` stream and an
`isCompressing` singleton, issues #317 and #307). Everything below the Dart layer already behaves
correctly per job; the only thing missing is the scheduling above it.
Output: a `maxConcurrentJobs` constructor parameter, a queued state on `CompressJob`, a unit suite
that proves ordering and the limit with no device at all, and real queued compressions proven on
the Android emulator.
</objective>

## Discretion resolved here (D-14)

Two shapes can satisfy D-01/D-02/D-04. This plan picks one so the executor does not have to.

**`CompressVideo`'s constructor stops being `const`.** A queue is per-instance mutable state, and
a `const` constructor forbids any non-constant field initialiser, so the queue cannot be an
instance field of a `const` class. The alternative — keeping `const` and hanging queue state off
an `Expando` keyed by the instance — was rejected because Dart canonicalises identical `const`
instances, so two `const CompressVideo()` expressions would silently share one queue, directly
contradicting D-04 for exactly the construction style the dartdoc currently recommends. The
package is unpublished (Phase 6 owns release), so the window to make this change for free is now.
`grep` confirms the only `const CompressVideo(` occurrence in the repository today is the
constructor declaration itself, so no call site changes.

**The queued state is exactly one new public member on `CompressJob`: `bool get isQueued`.**
05-CONTEXT.md's own "keep the public API additions minimal" line is the constraint; the queue's
ordering and limit are proven in tests through a fake host API that records the order of
`startCompress` calls, which needs no extra public surface.

<assumption_delta_decision>
**Noun that changes primacy:** `job` — the package was designed around one in-flight job at a
time on the Dart side (one `compress()` call, one `CompressJob`, one platform call issued
immediately) and becomes a *set of jobs with an admission policy* (a queue plus a concurrency
limit).

**Decision: `add-alongside`, not `promote`.** The singular per-job path stays primary and
completely unchanged — `CompressJob` is still the unit of progress, cancellation, result and
native identity, and the native engines still know only about individual jobs (D-01). The queue
is a new layer strictly *above* the existing singular path; nothing about a single job's
lifecycle is re-expressed in terms of the collection. Promoting the plural noun (for example, a
`CompressBatch` type owning several jobs' progress) would recreate exactly the global-stream
coupling this package was built to avoid.

**Invariant test warranted: yes.** Every job's progress and result must round-trip through the
identical per-job path regardless of queue position. Task 2 adds an explicit invariant helper
asserting, for each job in a submitted set: its progress values are non-decreasing, within 0–100,
terminate at exactly one 100 (or at cancellation), its stream closes before or as its result
resolves, and its `outputPath` is distinct from every other job's — with the same assertions
holding for the job that started immediately and for the job that waited.
</assumption_delta_decision>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| caller → `CompressVideo` constructor | `maxConcurrentJobs` is caller-supplied and bounds how much concurrent device work the plugin will initiate |
| queued job → platform call | An entry sitting in the Dart queue holds a path, a request and a job id that have already been validated but not yet sent |
| job completion → queue admission | The only thing that frees a slot; a bug here either starves the queue or over-subscribes the device |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-05-01 | Denial of Service | `maxConcurrentJobs` admitting unbounded concurrent encodes | medium | mitigate | Validated to be at least 1 at construction with a typed `unsupportedInput` failure; the default is 1, so the safe behaviour requires no caller action. | T-05-02 | Denial of Service | Queue starvation — a slot that is freed but never re-pumped, or an active count that drifts | high | mitigate | The cancel-while-queued path never touches the active count and the running-job completion hook owns the single pump call site; a dedicated unit case proves a later queued job still starts after an earlier queued job is cancelled (05-RESEARCH.md Pitfall 1) |
