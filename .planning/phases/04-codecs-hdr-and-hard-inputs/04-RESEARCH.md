## Summary

Phase 4 activates two reserved enum values (`VideoCodec.hevc`, `HdrMode.keepHdr`) that the Dart,
Android and Apple validation layers currently all reject outright, and it closes a real gap in
the audio pipeline (5.1/PCM). None of this needs a new dependency: Media3 1.11.1 (already pinned
in `android/build.gradle.kts`) ships every primitive this phase needs, including a public
capability-probing utility (`androidx.media3.transformer.EncoderUtil`) that the current codebase
does not yet use and should, in place of hand-rolled `MediaCodecList` prefix matching. On Apple,
the mechanism is a straight extension of the existing `AVAssetReader`/`AVAssetWriter` pipeline:
swap the reader's pixel format and the writer's codec/color-properties dictionary based on a
VideoToolbox hardware-encoder probe, mirroring what Android does with `Composition.setHdrMode`.

The single most consequential fact this research found by directly booting the project's own
AVD and pulling its live `media_codecs.xml`: **the `compress_video_api35` emulator has zero HEVC
encoders of any kind** -- not just no hardware one. Its `Encoders` section lists only
`OMX.google.h264.encoder`, `h263.encoder`, `mpeg4.encoder` and `vp8.encoder`; the only HEVC
entries anywhere are two *decoders* (`c2.goldfish.hevc.decoder`, `OMX.google.hevc.decoder`).
This directly confirms CONTEXT.md's assumption that the Android emulator only exercises the
HEVC/keep-HDR *fallback* path, and it means the capability probe does not need device-specific
tuning to get a correct fallback answer there -- `EncoderUtil.getSupportedEncoders("video/hevc")`
will simply return an empty list. The equivalent fact on Apple (found via search, not a local
Mac read, so MEDIUM confidence): the iOS Simulator has **no hardware video encoder at all**
(VideoToolbox hardware encode is unavailable in simulator targets), while every Apple Silicon
Mac -- including the `macos-latest` GitHub Actions runner CI already uses -- has a hardware
HEVC encoder via its Media Engine. That second fact is new information CONTEXT.md's own decision
text does not surface: **CI's existing macOS-host job can prove the real HEVC-success and
keep-HDR-success paths**, not just the fallback the iOS simulator and Android emulator are
limited to. The plan should treat the macOS host leg of `hard_inputs_test.dart` as a second,
real assertion target (`hevcFallback: false`, `videoCodec: 'hevc'`), not just a third fallback
run, while still keeping the "hardware checklist" for what only a physical Android phone and a
real iPhone camera clip (Dolby Vision profile 8 RPU) can prove.

A second important architectural finding: Media3's own default behavior for `HDR_MODE_KEEP_HDR`
(the mode's own default when unset) is to *automatically* step down to
`HDR_MODE_TONE_MAP_HDR_TO_SDR_USING_OPEN_GL` when the device can't keep HDR -- confirmed from the
official tone-mapping doc page. This is a useful safety net, but it only downgrades the HDR
*mode*, not the video MIME type: an app that always requests H.265 output would get HEVC 8-bit
SDR on fallback, not the H.264 fallback CDEC-03 requires. The plan must keep the independent
hardware-HEVC probe as the thing that decides H.264-vs-H.265 mime type, and treat Media3's
automatic HdrMode step-down as defense in depth, not the primary mechanism.

A third finding changes how AUDO-03 should be scoped: today, both engines only force an audio
re-encode when the source codec isn't AAC (`!sourceIsAAC` on Apple; the request explicitly says
`REENCODE` on Android). Neither currently forces a re-encode purely because the channel count is
too high. A 5.1 *AAC* source under the default `AudioPassthrough` option would, as the code
reads today, attempt to pass a 6-channel AAC track straight through -- not what CDEC-03/AUDO-03's
corpus test needs (stereo AAC, `audioReencoded: true`). This is a real, previously-undocumented
gap the plan must close on both platforms, not a "nothing needed" audio task.

**Primary recommendation:** wrap the existing `EditedMediaItem` in a `Composition` (via
`EditedMediaItemSequence.Builder(editedMediaItem).build()` then `Composition.Builder(sequence)`)
so `Transformer.start(Composition, path)` can be used instead of the current
`start(EditedMediaItem, path)` overload, set `HdrMode` there per CONTEXT.md's OpenGL-first/
MediaCodec-fallback policy, gate the H.264-vs-H.265 MIME type on `EncoderUtil.isHardwareAccelerated`
independently of the HdrMode fallback, and extend both platforms' "does audio need a forced
re-encode" condition to include "channel count > 2" alongside "codec isn't AAC".

### Pattern 1: Composition wrapping for HdrMode (Android)

**What:** `Transformer.start(EditedMediaItem, String)` (the overload `TransformerEngine.kt`
currently calls) has no way to set `HdrMode` — that lives on `Composition.Builder`. Wrap the
single `EditedMediaItem` in an `EditedMediaItemSequence`, then a `Composition`, and call the
`Transformer.start(Composition, String)` overload instead.

**When to use:** Whenever `request.hdrMode != "toneMapToSdr"`'s default OpenGL path needs an
explicit `HdrMode`, or whenever keep-HDR is requested. For a non-HDR source, building a
`Composition` with the default `HdrMode` (which is `HDR_MODE_KEEP_HDR`, harmless for
non-HDR content since there's nothing to keep) and calling the same overload unconditionally
is simpler than branching between two different `start` overloads — recommended so the code
path is identical whether or not HDR is in play.

**Example:**
```kotlin
// Source: androidx.media3.transformer.Composition, Composition.Builder, EditedMediaItemSequence
// (verified live via javap against the installed media3-transformer-1.11.1.aar; method
// signatures and int constant VALUES below are exact, not paraphrased)
// Composition$Builder.setHdrMode(int) — constants on Composition itself:
//   HDR_MODE_KEEP_HDR = 0
//   HDR_MODE_TONE_MAP_HDR_TO_SDR_USING_MEDIACODEC = 1
//   HDR_MODE_TONE_MAP_HDR_TO_SDR_USING_OPEN_GL = 2
//   HDR_MODE_EXPERIMENTAL_FORCE_INTERPRET_HDR_AS_SDR = 3
val sequence = EditedMediaItemSequence.Builder(editedMediaItem).build()
val composition = Composition.Builder(sequence)
    .setHdrMode(Composition.HDR_MODE_TONE_MAP_HDR_TO_SDR_USING_OPEN_GL)
    .build()
transformer.start(composition, tempFile.path)
```

### Pattern 2: OpenGL-first, MediaCodec-fallback, typed-error-last retry chain

**What:** There is no synchronous "will this HdrMode work on this device" query for the
tone-map paths (unlike the encoder capability query, which `EncoderUtil` answers directly)
[CITED: developer.android.com/media/media3/transformer/tone-mapping]. The official doc states
plainly: for `HDR_MODE_TONE_MAP_HDR_TO_SDR_USING_MEDIACODEC`, "If not supported, `Transformer`
throws an `ExportException`." The only way to know is to attempt the export and catch the
exception.

**When to use:** CDEC-02's default tone-map-to-SDR path, per CONTEXT.md's decision order
(OpenGL first — "Supported on API 29+, with generally wider support across devices" — then
MediaCodec — "Only supported on API 31+ on certain devices").

**Example:**
```kotlin
// Sequential attempt, not a capability pre-check (none exists for this path).
// ExportException.errorCode from a genuinely unsupported tone-map request is expected to land
// in ErrorMapping's EXISTING "unsupportedInput" bucket (ERROR_CODE_DECODING_FORMAT_UNSUPPORTED)
// or "encoderUnavailable" bucket (ERROR_CODE_ENCODING_FORMAT_UNSUPPORTED) or the
// ERROR_CODE_VIDEO_FRAME_PROCESSING_FAILED "io" bucket [VERIFIED:
// android/src/main/kotlin/com/danjjohnson/compress_video/ErrorMapping.kt:82-107 -- these three
// codes are already mapped, no new reasonForErrorCode branch is needed] -- confirm the EXACT
// code Media3 actually throws with a live run before trusting which bucket fires; do not
// hand-author a new mapping speculatively.
suspend fun runWithHdrFallback(buildAndRun: (Int) -> CompressResultMessage): CompressResultMessage {
    return try {
        buildAndRun(Composition.HDR_MODE_TONE_MAP_HDR_TO_SDR_USING_OPEN_GL)
    } catch (e: CompressVideoError) {
        try {
            buildAndRun(Composition.HDR_MODE_TONE_MAP_HDR_TO_SDR_USING_MEDIACODEC)
        } catch (e2: CompressVideoError) {
            throw CompressVideoError("unsupportedInput", "No supported HDR tone-map path on this device")
        }
    }
}
```
Each attempt needs its own fresh `Transformer`/temp file (a `Transformer` cannot be reused after
`onError`); budget for the plan to size this correctly rather than retrying against stale state.

### Pattern 3: Hardware HEVC gate via `EncoderUtil`, independent of `HdrMode`

**What:** `androidx.media3.transformer.EncoderUtil` [VERIFIED via `javap` against the installed
AAR — see Sources] exposes:
```
getSupportedEncoders(String mimeType): ImmutableList<MediaCodecInfo>
isHardwareAccelerated(MediaCodecInfo, String mimeType): boolean
getSupportedEncodersForHdrEditing(String mimeType, ColorInfo): ImmutableList<MediaCodecInfo>
isHdrEditingSupported(MediaCodecInfo, String mimeType, ColorInfo): boolean
```
**When to use:** Before deciding H.264-vs-H.265 mime type (CDEC-01) and before deciding whether
keep-HDR (CDEC-03) is achievable, independent of what `Composition`'s own automatic `HdrMode`
step-down does (Pattern 4 explains why these must stay independent).

**Example:**
```kotlin
val hevcEncoders = EncoderUtil.getSupportedEncoders(MimeTypes.VIDEO_H265)
val hasHardwareHevc = hevcEncoders.any { EncoderUtil.isHardwareAccelerated(it, MimeTypes.VIDEO_H265) }
// On the compress_video_api35 emulator this list is EMPTY [VERIFIED live: pulled
// /vendor/etc/media_codecs_google_video.xml from a booted instance of this exact AVD --
// its <Encoders> block lists only OMX.google.h263.encoder, .h264.encoder, .mpeg4.encoder,
// .vp8.encoder; zero video/hevc entries anywhere], so hasHardwareHevc is false without any
// prefix-matching logic being exercised at all on this device.

val requestHdrColorInfo = ColorInfo.Builder()
```

### Pattern 4: Composition's automatic `HdrMode` step-down is a safety net, not the mechanism

**What:** [CITED: developer.android.com/media/media3/transformer/tone-mapping] states: "By
default, Transformer sets this value to `HDR_MODE_KEEP_HDR` ... If the device does not support
the HDR format, Transformer automatically attempts to use
`HDR_MODE_TONE_MAP_HDR_TO_SDR_USING_OPEN_GL` instead." This means requesting `HDR_MODE_KEEP_HDR`
on an incapable device does NOT throw — it silently produces tone-mapped SDR. But the video MIME
type requested (`setVideoMimeType`) is a *separate* Transformer/Composition setting that this
automatic step-down does not touch.

**Why it matters:** If the app always requested H.265 output whenever keep-HDR was asked for,
and relied solely on this automatic HdrMode step-down for the "incapable device" case, the
result on an incapable device would be **HEVC 8-bit SDR**, not the H.264 SDR fallback CDEC-03's
contract requires ("falls back to tone-mapped SDR" implies the whole encode plan reverts, not
just the HDR mode). The app's own `EncoderUtil.isHardwareAccelerated`/`getSupportedEncodersForHdrEditing`
probe (Pattern 3) must independently gate the MIME type choice; Media3's automatic HdrMode
step-down is then just extra insurance against a probe/reality mismatch, not the primary
fallback mechanism.

### Pattern 5: HDR reporting via `ExportResult.colorInfo` + `ColorInfo.isTransferHdr`

**What:** `ExportResult.colorInfo: ColorInfo` [VERIFIED via `javap`] carries the OUTPUT's actual
color transfer; `ColorInfo.isTransferHdr(ColorInfo): boolean` [VERIFIED via `javap`] is a public
static helper. `toneMapped` should be computed as: input was HDR (already known from
`Probe.kt.isHdr`, computed before the export) AND the output's `colorInfo` is no longer HDR
(`!ColorInfo.isTransferHdr(exportResult.colorInfo)`) AND the codec path was not `usedOriginal`
(a copied original is never "tone-mapped," matching the existing `usedOriginal` guard pattern
already used for `transmuxed`/`audioReencoded` in `finishSuccess`).

**Example:**
```kotlin
// buildResultFromDestination currently hardcodes toneMapped = false, hevcFallback = false
// (TransformerEngine.kt:465-471) -- replace with:
val outputIsHdr = exportResult.colorInfo?.let { ColorInfo.isTransferHdr(it) } ?: false
val toneMapped = !usedOriginal && inputWasHdr && !outputIsHdr
```

### Anti-Patterns to Avoid
- **Trusting `Composition`'s automatic `HdrMode` step-down as the whole fallback mechanism:**
  it silently changes the HDR mode but not the MIME type (Pattern 4) — would produce HEVC SDR
  instead of the required H.264 SDR fallback.
- **Reusing a `Transformer`/`AVAssetWriter` instance across a fallback retry:** both are
  documented single-use; a failed attempt must build a fresh instance and a fresh temp file
  before the next attempt in the OpenGL→MediaCodec chain (Pattern 2).
  This mirrors the existing "fresh Transformer per compress() call" pattern already in
  `TransformerEngine.kt` — no change needed there beyond looping the pattern.
- **Assuming a passthrough-mode 5.1 AAC source is safe today:** it is not (see Common Pitfalls);
  do not treat AUDO-03 as "downmix logic already exists, just wire it up" without extending the
  re-encode trigger condition.
- **Asserting only the fallback path on the macOS-host CI leg:** given the verified Apple
  Silicon Media Engine fact above, doing so would forgo real coverage CI can already give for
  free.

## Common Pitfalls

### Pitfall 1: Passthrough mode does not force a downmix for high channel counts today
**What goes wrong:** A 5.1 AAC-encoded corpus clip, compressed under the DEFAULT
`AudioPassthrough` option (what the phase's own success criteria imply — "compress ... with
default options"), would not trigger either engine's existing forced-re-encode branch:
Android's `TransformerEngine.compress` only builds a `ChannelMixingAudioProcessor` when
`request.audioMode == AudioModeMessage.REENCODE` [VERIFIED:
android/src/main/kotlin/com/danjjohnson/compress_video/TransformerEngine.kt:133-134 —
`if (request.audioMode == AudioModeMessage.REENCODE && requestedAudioChannels != null && ...)`];
Apple's `audioWillReencode` is `includeAudio && (request.audioMode == .reencode || !sourceIsAAC)`
[VERIFIED: darwin/compress_video/Sources/compress_video/CompressionEngine.swift:161 —
`let audioWillReencode = includeAudio && (request.audioMode == .reencode || !sourceIsAAC)`] —
neither condition checks channel count.
**Why it happens:** The passthrough-fallback design (Phase 2/3) was built to solve "source
codec isn't AAC," not "source has too many channels." AUDO-03 is a genuinely new condition,
not a rewiring of existing logic.
**How to avoid:** Extend both conditions to also force a re-encode when the source's channel
count exceeds the container's stereo default (`inputAudioChannels != null && inputAudioChannels > 2`
on Android; `(sourceAudioChannelCount ?? 2) > 2` on Apple), defaulting the target channel count
to 2 for this forced case specifically (not requiring the caller to have set an explicit
`AudioReencode(channels: 2)` — the phase's own decision text says 5.1 downmixes to stereo
*under default options*, so the target of "2" must be an engine-side default for this forced
path, not something read from `request.audioChannels`, which is `null` under `AudioPassthrough`).
**Warning signs:** A 5.1 AAC corpus fixture compresses "successfully" (no crash) but the output
still carries 6 channels and `audioReencoded: false` — technically not a crash, but not what
AUDO-03 asks for either.

### Pitfall 2: Composition's automatic HdrMode fallback masks a MIME-type mismatch
See Pattern 4 above — repeated here as a pitfall because it is easy to implement CDEC-03 in a
way that "works" (no crash, output plays) but produces HEVC SDR instead of the required H.264
SDR fallback, and no existing test would catch this unless the corpus assertion explicitly
checks `videoCodec` on the fallback case, not just `toneMapped`/`hevcFallback`.

### Pitfall 3: No synchronous capability check exists for the tone-map (not keep-HDR) paths
**What goes wrong:** Unlike the encoder capability question (`EncoderUtil` answers it directly),
there is no pre-flight query for "will `HDR_MODE_TONE_MAP_HDR_TO_SDR_USING_OPEN_GL` succeed on
this device." The only way to find out is to attempt the export.
**Why it happens:** OpenGL tone-mapping support depends on runtime GL extension availability
(`GL_EXT_YUV_target` and similar), which Android does not expose through `MediaCodecList` or any
other static capability table.
**How to avoid:** Structure the code as the sequential try/catch chain in Pattern 2, with each
attempt building a fresh `Transformer`. Do not attempt to pre-guess support from API level alone
(API 29+ is necessary but the doc says "with generally wider support," not "guaranteed").
**Warning signs:** A plan or task that says "check support, then encode once" for the tone-map
default path is describing an API that does not exist for this specific decision (it exists for
`isHdrEditingSupported`/keep-HDR, but not for the tone-map paths).

### Pitfall 4: The emulator's software HEVC *decoder* existing does not prove Main10 profile decode works
**What goes wrong:** `c2.goldfish.hevc.decoder` and `OMX.google.hevc.decoder` are both listed in
the emulator's codec XML [VERIFIED live], which proves the emulator can extract/demux HEVC and
almost certainly decode 8-bit Main profile — but the XML declares no explicit HDR/10-bit feature
flag (`dynamic-color-aspects` is present on the H.264/VP8/VP9 decoders but conspicuously ABSENT
from both HEVC decoder entries [VERIFIED, same XML pull]). Whether the goldfish HEVC decoder
handles Main10 (10-bit) profile streams — required to even READ the HLG10/PQ10 corpus clips
before any tone-mapping can happen — is NOT provable from the XML alone.
**Why it happens:** `media_codecs.xml`'s `<Limit>`/`<Feature>` tags describe container-level
constraints (size, bitrate, framerate); profile/level support for a `c2.*` codec is often
negotiated at the native HAL layer and is not fully reflected in this XML on every Android
version.
**How to avoid:** Treat this as an Open Question the plan's own execution (not this research)
must resolve empirically: the very first `hard_inputs_test.dart` run against a real HLG10 corpus
clip on the Android emulator IS the test of this. If it fails to even decode (not just fails to
tone-map), the error will be `ERROR_CODE_DECODING_FORMAT_UNSUPPORTED`/`DECODER_INIT_FAILED`
rather than a tone-mapping-specific one — already mapped to `unsupportedInput`/`decoderUnavailable`
respectively by the existing `ErrorMapping.kt` table, so no new error-mapping code is needed
regardless of which failure actually occurs.
**Warning signs:** A plan that asserts `toneMapped: true` for the HLG10 clip on the Android
emulator without a documented fallback for "the clip doesn't decode at all on this specific
emulator" is assuming a Main10 decode capability this research could not confirm from static
config alone.

### Pitfall 5: PCM-in-MP4 container compatibility is unverified end-to-end
**What goes wrong:** ffmpeg happily muxes `pcm_s16le` into an `.mp4` container [VERIFIED live:
`ffmpeg -c:a pcm_s16le ... /tmp/test_pcm.mp4` exits 0, `ffprobe` reads it back correctly], but
MP4 (ISO BMFF) support for raw LPCM audio tracks is less universal than QuickTime `.mov`'s
`lpcm`/`sowt`/`twos` fourccs; MediaExtractor/AVAssetReader compatibility with an ffmpeg-authored
PCM-in-MP4 track is not verified in this session (would require running the actual integration
suite, out of this research's scope per the task's own instruction not to run `flutter test`).
**Why it happens:** The corpus-generation script has never produced a PCM audio fixture before
(AUDO-03 is new in this phase); Phase 1's corpus is en tirely AAC audio.
**How to avoid:** Generate the fixture, and let the plan's own first integration-test run be the
proof — if `MediaExtractor`/`AVAssetReader` reject the container/codec combination outright, the
existing typed-error path (`unsupportedInput`/`decoderUnavailable`) already handles it, but the
phase's own success criterion ("compress ... without an error") would then require either a
`.mov`-flavored fixture (same codec, more standard container for LPCM) or an alternate PCM
fourcc. Flag this as a fixture-format decision to make explicit in the plan, not something to
assume works.

### Pitfall 6: Emulator/simulator absence of a HEVC encoder is total, not partial
Already covered above (Summary) but repeated as a pitfall because CONTEXT.md's own wording
("The Android emulator and the iOS simulator have no hardware HEVC encoder") is easy to
misread as "no HARDWARE encoder, but maybe a software one exists to test the mime-type
plumbing." Verified live: there is no HEVC encoder of ANY kind on this project's own AVD. A test
that tries to assert "software HEVC encode as a middle case" on the emulator will not find one
to exercise.

## Open Questions

1. **Does the emulator's goldfish HEVC decoder handle Main10 (10-bit) profile streams?**

     `dynamic-color-aspects` feature flag is present on other decoders but absent from both HEVC
     entries in the XML.
   - What's unclear: whether this is meaningful (feature flag genuinely absent) or just how this
     Android version's codec XML happens to be authored for `c2.*` codecs.
   - Recommendation: the plan's first `hard_inputs_test.dart` run against the synthetic HLG10/PQ10

     that specific platform/clip combination.

2. **Exact `ExportException.errorCode` thrown for an unsupported tone-map request on THIS emulator.**
   - What we know: the official doc names the exception type (`ExportException`) for the
     MediaCodec path specifically, and the existing `ErrorMapping.kt` table already covers every
     plausible code (`DECODING_FORMAT_UNSUPPORTED`, `ENCODING_FORMAT_UNSUPPORTED`,

   - What's unclear: which SPECIFIC code fires for an OpenGL-path failure (the doc doesn't say —
     it only documents the MediaCodec path's failure explicitly).
   - Recommendation: no code change needed regardless of the answer (all plausible codes already
     map correctly); this only affects which specific `CompressVideoErrorReason` a real API<29
     device would see, which is out of CI's reach anyway (emulator is API 35).

3. **Whether GitHub Actions' `macos-latest` is Apple Silicon for THIS repo's actual runs.**
   - What we know: GitHub's changelog confirms arm64-by-default as of macOS 26 GA (2026-02-26).
   - What's unclear: whether this specific repo/org has any pinned older label or Intel opt-in
     that would change the assigned runner.
   - Recommendation: the plan's first CI run against the new suite should log `uname -m`/
     `sysctl -n machdep.cpu.brand_string` on the macOS job as a cheap confirmation step before

4. **PCM-in-MP4 vs PCM-in-.mov for the AUDO-03 fixture.**
   - What we know: ffmpeg muxes PCM into MP4 without complaint.
   - What's unclear: whether `MediaExtractor`/`AVAssetReader` accept it without a fourcc/format
