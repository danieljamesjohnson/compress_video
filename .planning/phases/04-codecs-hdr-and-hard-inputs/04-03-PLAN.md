<objective>
Turn the two reserved enum values into real, honest behaviour on Android: HEVC only where a
hardware encoder exists, keep-HDR only where the device can genuinely keep it, and a reported
fallback in every other case.

Purpose: CDEC-01 and CDEC-03 are the two requirements a naive implementation "passes" while being
wrong — request HEVC, get HEVC-shaped output from a software encoder nobody wanted; request
keep-HDR, get HEVC 8-bit SDR because Media3 quietly stepped the HDR mode down and left the MIME
type alone. Both failure modes are documented in research and both are invisible unless the test
asserts the codec, not just the flag.
Output: a capability probe unit-tested without hardware, an independent MIME gate, a keep-HDR
gate that agrees with it, and integration cases whose expectations are chosen by the capability
the result reports rather than by the platform's name.
</objective>

| ID | 04-CONTEXT.md decision |
|----|------------------------|
| D-05 | Hardware HEVC detection: Android enumerates the codec list for a `video/hevc` encoder that is not a software codec; the emulator and simulator have none, so CI exercises the fallback path and HEVC success lives in the hardware checklist. |
| D-06 | HEVC fallback is reported through the existing `hevcFallback: true` result field with H.264 output. No new field. |
| D-07 | Keep-HDR output is HEVC Main10 carrying the source's transfer function with BT.2020 primaries; Android via Media3 `HDR_MODE_KEEP_HDR`; requires a hardware HEVC 10-bit encoder, otherwise fall back. |
| D-08 | Keep-HDR fallback is tone-mapped SDR H.264 reported as `toneMapped: true` and `hevcFallback: true`; "keep-HDR requested and `toneMapped: true`" means the fallback happened. No new result field. |

**Research override to D-05 (04-RESEARCH.md, Summary and "Don't Hand-Roll"):** use Media3's own
`EncoderUtil.getSupportedEncoders` / `isHardwareAccelerated` / `getSupportedEncodersForHdrEditing`
instead of the hand-rolled `MediaCodecList` prefix matching D-05's literal text describes. The
library ships and tests this, the platform's own `MediaCodecInfo.isHardwareAccelerated()` (API
29+) is the authoritative source underneath it, and a prefix scan cannot answer the HDR-editing
question at all. The prefix list stays only as the documented pre-API-29 fallback.

**Research override to D-17 (04-RESEARCH.md, Summary and Pattern 7):** the macOS CI host is an
Apple Silicon runner with a hardware HEVC encoder, so one CI leg can prove the real success path
rather than only the fallback. D-17 remains exactly true of the iOS simulator and the Android
emulator, which is where this plan runs. The suite is therefore written so the expectation is
chosen by the capability the result reports, and 04-04 turns that into a real success assertion
on macOS without rewriting a single case.

<assumption_delta_decision>
**Noun now primary:** the *requested* codec/HDR mode and the *actual* codec/HDR outcome become
two different things for the first time. Before this phase, `videoCodec` in a result was always
`h264` and the request could only ever ask for `h264`, so "requested" and "actual" were the same
noun and nothing had to name the difference.

**Decision: `no-change` to the contract, with an invariant test added.** `CompressResult` already
carries `videoCodec` (actual), `hevcFallback` (the request was not honoured) and `toneMapped`
(the HDR outcome). Those three name the difference correctly and 04-CONTEXT.md twice states that
no new field is wanted. Promoting a `requestedCodec` field, or adding an `actualHdrMode` enum,
would widen the Pigeon contract for information the caller already has (it made the request) plus
one flag it already receives.

**Rationale:** the risk this delta creates is not a missing field, it is a *consistency* risk —
a result that says `hevcFallback: true` while `videoCodec` reads `hevc`, or `toneMapped: true`
on a file that is still HDR, would be internally incoherent and no existing test would catch it.
So this plan adds an invariant assertion to `hard_inputs_test.dart` that runs on every codec and
HDR case on every platform: exactly one coherent combination is allowed, checked against a
re-probe of the produced file. That is the test the delta warrants.
</assumption_delta_decision>

**Apple-side skip guards:** as in 04-02, guard every new case with the same Android-only skip
argument `compress_test.dart` used in commit `2007973` (a `skip:` argument negating
`Platform.isAndroid`); 04-04 removes them.
